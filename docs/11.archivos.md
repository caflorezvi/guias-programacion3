# Manejo de archivos

El manejo de archivos en Elixir se realiza principalmente a través de tres módulos: `File`, `IO` y `Path`. Con ellos es posible leer, escribir y manipular tanto archivos como directorios siguiendo un enfoque funcional y seguro. A continuación, se presentan los conceptos que se abordarán en esta guía:

- Lectura de archivos con `File.read/1` y manejo del resultado con tuplas.
- Escritura de archivos con `File.write/2` y sus opciones.
- Construcción de rutas portables con el módulo `Path` y `__DIR__`.
- Lectura perezosa de archivos grandes con `File.stream!/1`.
- Escritura incremental con `File.open/2` y el módulo `IO`.
- Manejo de directorios: listar, filtrar y crear carpetas.

Este enfoque es coherente con los principios funcionales que hemos visto a lo largo del curso:

- Los datos que se leen son **inmutables**, igual que cualquier otro valor del lenguaje.
- La mayoría de las operaciones devuelven una **tupla de resultado** (`{:ok, resultado}` o `{:error, razón}`), lo que permite manejar tanto el éxito como el error de forma explícita mediante **pattern matching**, sin recurrir a excepciones.
- Para los casos en que se prefiere que un fallo detenga el programa, existen variantes terminadas en `!` que **lanzan una excepción** en lugar de devolver una tupla.
- Cuando se trabaja con archivos grandes, los **streams** permiten procesarlos de forma perezosa, leyéndolos por partes sin cargarlos completos en memoria.

## Ejemplo 1: Analizador de registros del servidor

Un **servidor** es un computador que permanece encendido prestando un servicio a otros equipos, como el que aloja la página web de la universidad. Nadie está sentado frente a él, así que escribe todo lo que hace en un archivo de texto llamado **log** (registro). Cada vez que ocurre algo relevante **agrega una línea al final** con la fecha, la hora, un **nivel de severidad** y una descripción. Si el sistema se cae de madrugada, la causa está ahí.

Los tres niveles más comunes son `INFO` (algo normal ocurrió), `WARN` (una advertencia) y `ERROR` (algo falló). Como el servidor no para, estos archivos **crecen sin límite** y pueden pesar varios gigabytes, así que revisarlos a mano es inviable.

El equipo de soporte de una empresa necesita una herramienta para analizar ese log, pero **no la pide toda de una vez**. Como en un proyecto real, cada versión traerá un requerimiento nuevo que obligará a mejorar la solución. Empezaremos por lo mínimo y de ahí en adelante cada versión resolverá un problema que la anterior dejó al descubierto.

Primero, cree un archivo `servidor.log` con el siguiente contenido para trabajar. El formato de cada línea es *fecha, hora, nivel y descripción*.

```
2026-08-01 10:15:02 INFO Usuario carlos inicio sesion
2026-08-01 10:15:47 ERROR Fallo de conexion con la base de datos
2026-08-01 10:16:03 INFO Usuario luis inicio sesion
2026-08-01 10:18:22 WARN Memoria al 85 por ciento
2026-08-01 10:19:10 ERROR Timeout al consultar el servicio de pagos
2026-08-01 10:21:35 INFO Usuario carlos cerro sesion
2026-08-01 10:22:01 ERROR Fallo de conexion con la base de datos
```

Junto a ese archivo, cree otro llamado `reporte.exs`, donde iremos escribiendo el programa. **Después de cada versión, ejecútelo** desde la terminal para comprobar el resultado:

```bash
elixir reporte.exs
```

### Versión 0: Ver qué hay dentro del archivo

El primer reto es **abrir el archivo y mostrarlo en pantalla**. Para eso basta `File.read/1`, que recibe la ruta del archivo y devuelve su contenido completo como una cadena de texto.

```elixir
defmodule Reporte do
  def main do
    {:ok, contenido} = File.read("servidor.log")
    IO.puts(contenido)
  end
end

Reporte.main()
```

Al ejecutarlo verá el log completo impreso en la consola.

En este código no hay nada nuevo, salvo `File.read/1`. La línea `{:ok, contenido} = File.read("servidor.log")` es coincidencia de patrones pura. La función devuelve una tupla con la convención `{:ok, valor}` / `{:error, motivo}` y el operador `=` la descompone enlazando el texto a la variable `contenido`. Casi todas las funciones del módulo `File` siguen esa convención.

**Ahora provoque el error.** Cambie el nombre del archivo por uno que no exista y vuelva a ejecutar:

```elixir
{:ok, contenido} = File.read("no_existe.log")
```

El programa se detiene con este mensaje:

```
** (MatchError) no match of right hand side value:

    {:error, :enoent}
```

Es un `MatchError`. El patrón de la izquierda exige un `:ok`, la función devolvió `{:error, :enoent}` y las formas no coinciden. Ahí está el problema que debe resolver la siguiente versión, porque un archivo puede no existir y el programa tiene que **manejar ese caso** en lugar de reventar.

### Versión 1: Contar las líneas y manejar el error

Ahora sí vamos con el requerimiento completo, que es contar cuántas líneas tiene el log y cuántos errores contiene. Y, a partir de lo que acabamos de ver, manejar los dos resultados posibles de `File.read/1` con un `case` en lugar de una coincidencia directa:

```elixir
defmodule Reporte do
  def main do
    analizar("servidor.log")
    analizar("no_existe.log")   # Para comprobar el manejo de errores
  end

  defp analizar(ruta) do
    case File.read(ruta) do
      {:ok, contenido} ->
        lineas = String.split(contenido, "\n", trim: true)
        errores = Enum.count(lineas, &String.contains?(&1, "ERROR"))

        IO.puts("Líneas totales: #{length(lineas)}")
        IO.puts("Errores encontrados: #{errores}")

      {:error, :enoent} ->
        IO.puts("Error: el archivo no existe")

      {:error, razon} ->
        IO.puts("Error al leer el archivo: #{razon}")
    end
  end
end

Reporte.main()
```

Al ejecutar `elixir reporte.exs` debería ver:

```
Líneas totales: 7
Errores encontrados: 3
Error: el archivo no existe
```

Dos detalles del código:

- `String.split(contenido, "\n", trim: true)` parte el texto en una lista de líneas. La opción `trim: true` descarta las cadenas vacías; sin ella, el salto de línea final del archivo produciría una última línea vacía y el conteo saldría en 8.
- `Enum.count(lineas, &String.contains?(&1, "ERROR"))` cuenta solo los elementos que cumplen la condición. 

Compare este resultado con la Versión 0. **La segunda llamada, con un archivo inexistente, ya no revienta el programa**, sino que informa el error y continúa. Esa es la ventaja de que `File.read/1` devuelva una tupla en vez de lanzar una excepción, ya que el fallo termina siendo un valor más, que se maneja con las mismas herramientas que cualquier otro dato.

**Códigos de error comunes.** El átomo que acompaña a `{:error, razón}` indica qué salió mal. Los más frecuentes son:

- `:enoent`: El archivo no existe (No such file or directory)
- `:eacces`: Permiso denegado
- `:eisdir`: Es un directorio, no un archivo
- `:enotdir`: Se esperaba un directorio, pero no lo es
- `:enomem`: Memoria insuficiente

> ⚠️ **Nota:** casi toda función de `File` tiene una variante con `!` (`File.read!/1`, `File.write!/2`, …) que **lanza una excepción** en lugar de devolver una tupla. Úsela cuando prefiera que el programa falle de inmediato ante un error, en vez de manejarlo.

### Versión 2: Guardar el reporte en un archivo

**Nuevo requerimiento:** el resultado no puede quedarse en la pantalla. Debe guardarse en un archivo `reporte.txt`, para poder adjuntarlo al informe semanal del área.

Reemplazamos las impresiones por un texto que se escribe con `File.write/2` y de paso **separamos responsabilidades**, dejando una función que construye el reporte y otra que lo guarda.

```elixir
defmodule Reporte do
  def main do
    analizar("servidor.log", "reporte.txt")
  end

  defp analizar(ruta_log, ruta_reporte) do
    case File.read(ruta_log) do
      {:ok, contenido} ->
        contenido
        |> generar_texto()
        |> guardar(ruta_reporte)

      {:error, razon} ->
        IO.puts("Error al leer el archivo: #{razon}")
    end
  end

  # Función pura: recibe el contenido y devuelve el texto del reporte
  defp generar_texto(contenido) do
    lineas = String.split(contenido, "\n", trim: true)
    errores = Enum.count(lineas, &String.contains?(&1, "ERROR"))

    """
    === Reporte del log ===
    Líneas totales: #{length(lineas)}
    Errores encontrados: #{errores}
    """
  end

  # Efecto secundario aislado: escribir en disco
  defp guardar(texto, ruta) do
    case File.write(ruta, texto) do
      :ok -> IO.puts("Reporte generado en #{ruta}")
      {:error, razon} -> IO.puts("No se pudo escribir el reporte: #{razon}")
    end
  end
end

Reporte.main()
```

`generar_texto/1` es una **función pura**, los efectos secundarios quedaron confinados a `analizar/2` y `guardar/2`, siguiendo el principio de **minimizar y aislar** los efectos secundarios.

Aquí el `case` se simplificó a **una sola cláusula de error**, porque se eliminó la de `{:error, :enoent}`. Ya sabemos que el átomo viaja dentro de la tupla, así que `{:error, razon}` los cubre todos e imprime el motivo tal cual. Distinguir un código específico, como se hizo en la Versión 1, solo vale la pena cuando se quiere dar un mensaje distinto para ese caso.

Ejecute el programa. En la consola solo verá `Reporte generado en reporte.txt`, pero **junto a su script aparecerá un archivo nuevo**, `reporte.txt`, con este contenido:

```
=== Reporte del log ===
Líneas totales: 7
Errores encontrados: 3
```

El `"""` (*heredoc*) permite escribir un texto de varias líneas sin tener que concatenar `\n` a mano.

**Opciones de escritura.** `File.write/2` **sobrescribe** el archivo. Si en lugar de eso quisiéramos ir acumulando reportes, se usa la opción `:append`:

```elixir
# Agregar al final sin sobrescribir
File.write("historico.txt", "Nueva entrada\n", [:append])

# Múltiples opciones (:utf8 asegura el manejo correcto de tildes y eñes)
File.write("historico.txt", "datos", [:append, :utf8])
```

#### Una alternativa con `with`

El programa encadena **dos operaciones que pueden fallar**, leer el log y escribir el reporte. Es exactamente el caso que resuelve la estructura `with`. Así, `analizar/2` y `guardar/2` quedan en una sola función, sin anidamientos:

```elixir
defp analizar(ruta_log, ruta_reporte) do
  with {:ok, contenido} <- File.read(ruta_log),
       :ok <- File.write(ruta_reporte, generar_texto(contenido)) do
    IO.puts("Reporte generado en #{ruta_reporte}")
  else
    {:error, razon} -> IO.puts("Error: #{razon}")
  end
end
```

Las dos versiones son igual de válidas, así que use la que le resulte más legible.

### Versión 3: Rutas que no dependan de dónde se ejecute

**Nuevo requerimiento:** el análisis se ejecutará de forma automática cada noche mediante una tarea programada del sistema, que invoca el script desde otra carpeta. El programa debe funcionar sin importar desde dónde se ejecute.

Y aquí aparece un problema, ya que el programa anterior funciona **solo si se ejecuta desde la carpeta donde está el log**. Si se ejecuta `elixir carpeta/reporte.exs` desde otra carpeta, `File.read("servidor.log")` falla con `:enoent`, porque la ruta es relativa a la carpeta actual de la terminal y no a la del script.

La solución es construir las rutas a partir de `__DIR__`, que siempre apunta a la carpeta del archivo `.exs`, y unirlas con `Path.join/2` para que funcionen en cualquier sistema operativo:

En el archivo de la Versión 2, agregue los dos atributos al inicio del módulo y cambie `main`. El resto del módulo no se toca.

```elixir
defmodule Reporte do
  @log Path.join(__DIR__, "servidor.log")
  @salida Path.join(__DIR__, "reporte.txt")

  def main do
    analizar(@log, @salida)
  end

  # analizar/2, generar_texto/1 y guardar/2 quedan tal como estaban
end
```

Ese es todo el cambio. Las tres funciones que hacen el trabajo no se enteran, ya que construir una ruta no tiene nada que ver con leer el log ni con armar el reporte. Ese es el beneficio de haber separado responsabilidades: un cambio en el manejo de archivos no obliga a tocar la lógica del reporte.

Hay un detalle más sobre los **atributos de módulo**. Hasta ahora los habíamos usado para guardar valores literales (`@minimo 1`), pero aquí guardan el **resultado de una expresión** (`Path.join(__DIR__, "servidor.log")`). Eso es válido porque el atributo se resuelve **al compilar**, de modo que Elixir ejecuta `Path.join/2` una sola vez, en ese momento, y deja la ruta ya construida incrustada en el código.

Ahora el programa se puede ejecutar desde cualquier carpeta. **Compruébelo:** sitúese en otro directorio y ejecute el script indicando su ruta completa. Antes fallaba con `:enoent`; ahora funciona igual.

```bash
cd ..
elixir carpeta_del_proyecto/reporte.exs
```

`Path.join/2` es preferible a concatenar la ruta con `<>` porque usa el separador correcto de cada sistema operativo, `/` en Linux y macOS y `\` en Windows.

### Versión 4: Cuando el log es demasiado grande

**Nuevo requerimiento:** el reporte se queda corto. Ahora quieren saber **cuántos eventos hay de cada tipo** (`INFO`, `WARN`, `ERROR`), no solo cuántos errores. Y hay una complicación, y es que el programa va a correr sobre el log real de producción, que pesa **varios gigabytes**.

Ese último punto rompe la solución actual, ya que `File.read/1` carga **todo el archivo en memoria**. Con un log de prueba de 7 líneas no hay problema, pero con uno de varios gigabytes el programa se quedaría sin memoria antes de empezar a contar.

Aquí entra `File.stream!/1`, que aplica a un archivo la **evaluación perezosa** estudiada en la guía anterior. En lugar de devolver el contenido, devuelve una *receta* para producir las líneas una por una. Solo cuando una función de `Enum` empieza a consumirlo, el stream va leyendo del disco la línea que le piden, la entrega y pasa a la siguiente.

El siguiente diagrama muestra el impacto en la memoria de `File.read/1` frente a `File.stream!/1`:

![Diagrama de memoria](res/file_read_vs_stream.svg)

La implementación del módulo `Reporte`, utilizando `Stream` e incorporando el nuevo requerimiento, queda de la siguiente manera:

```elixir
defmodule Reporte do
  @log Path.join(__DIR__, "servidor.log")
  @salida Path.join(__DIR__, "reporte.txt")

  def main do
    contar_por_nivel()
    |> generar_texto()
    |> guardar(@salida)
  end

  defp contar_por_nivel do
    @log
    |> File.stream!()                  # Produce las líneas una por una
    |> Enum.frequencies_by(&nivel/1)   # Cuenta cuántas hay de cada nivel
  end

  # Determina el nivel de severidad de una línea
  defp nivel(linea) do
    cond do
      String.contains?(linea, "ERROR") -> "ERROR"
      String.contains?(linea, "WARN") -> "WARN"
      true -> "INFO"
    end
  end

  defp generar_texto(conteo) do
    lineas =
      conteo
      |> Enum.map(fn {nivel, cantidad} -> "#{nivel}: #{cantidad}" end)
      |> Enum.join("\n")

    """
    === Eventos por nivel ===
    #{lineas}
    """
  end

  defp guardar(texto, ruta) do
    case File.write(ruta, texto) do
      :ok -> IO.puts("Reporte generado en #{ruta}")
      {:error, razon} -> IO.puts("No se pudo escribir el reporte: #{razon}")
    end
  end
end

Reporte.main()
```

El contenido de `reporte.txt` queda así:

```
=== Eventos por nivel ===
ERROR: 3
INFO: 3
WARN: 1
```

Observe qué cambió y qué no. `guardar/2` quedó **intacta**, ya que escribir un texto en disco es independiente de cómo se haya producido ese texto. `generar_texto/1`, en cambio, **sí tuvo que reescribirse**. Al cambiar el requerimiento del reporte, dejó de recibir el contenido crudo del archivo y ahora recibe un mapa con el conteo (`%{"ERROR" => 3, "INFO" => 3, "WARN" => 1}`).

En `contar_por_nivel/0` vale la pena mirar el orden del pipeline. `File.stream!/1` no lee nada todavía, solo describe cómo producir las líneas; es `Enum.frequencies_by/2` la que **dispara** el recorrido y va pidiéndolas una por una. También aparece una **captura**, `&nivel/1`, que referencia una función privada del módulo actual sin necesidad de nombrarlo.

### Versión 5 (opcional): Escribir mientras se procesa

**Último requerimiento:** el reporte único ya no sirve. Ahora se piden **dos archivos separados**, porque los consume gente distinta:

- `errores.txt`, con **el detalle de cada línea de error**, para que el equipo técnico las revise sin abrir el log completo.
- `resumen.txt`, con **el conteo de eventos por nivel**, que es lo único que necesita la coordinación para su informe.

Esta separación revela algo interesante, y es que los dos archivos tienen **naturalezas opuestas**, por lo que conviene escribirlos de forma distinta. Para el resumen basta `File.write/2` al final, como veníamos haciendo. Pero acumular en memoria todas las líneas de error nos devolvería al problema que acabamos de resolver, así que ese archivo hay que abrirlo con `File.open/2` y escribir cada línea **a medida que se encuentra**, usando el módulo `IO`.

`File.open/2` recibe la ruta y el **modo** de apertura (`:read` para lectura, `:write` para escritura, que crea o sobrescribe el archivo, y `:append` para agregar al final), y devuelve `{:ok, dispositivo}` o `{:error, razón}`.

Es el mismo módulo `IO` que usamos para la consola (`IO.puts/1`, `IO.gets/1`), porque `IO` opera sobre **dispositivos** y tanto la consola como un archivo abierto lo son. Así la lectura nunca carga el log completo, y las líneas de error se escriben una a una:

```elixir
defmodule Reporte do
  @log Path.join(__DIR__, "servidor.log")
  @errores Path.join(__DIR__, "errores.txt")
  @resumen Path.join(__DIR__, "resumen.txt")

  def main do
    escribir_errores()
    escribir_resumen()

    IO.puts("Errores detallados en #{@errores}")
    IO.puts("Resumen generado en #{@resumen}")
  end

  # Archivo grande: se abre y se escribe poco a poco, a medida que se encuentran
  defp escribir_errores do
    {:ok, salida} = File.open(@errores, [:write, :utf8])
    IO.puts(salida, "=== Detalle de errores ===")

    lineas()
    |> Stream.filter(fn linea -> nivel(linea) == "ERROR" end)
    |> Enum.each(fn linea -> IO.puts(salida, linea) end)   # Escribe en el archivo

    File.close(salida)             # Siempre cerrar el archivo
  end

  # Archivo pequeño: se construye el texto completo y se escribe de una sola vez
  defp escribir_resumen do
    texto =
      lineas()
      |> Enum.frequencies_by(&nivel/1)
      |> Enum.map(fn {nivel, cantidad} -> "#{nivel}: #{cantidad}" end)
      |> Enum.join("\n")

    File.write(@resumen, "=== Eventos por nivel ===\n" <> texto <> "\n")
  end

  # Prepara el stream de líneas, reutilizado por las dos funciones.
  # Aquí hace falta String.trim/1: File.stream!/1 entrega cada línea con su
  # salto de línea (\n) al final, y IO.puts/2 agrega el suyo, así que el archivo de errores
  # saldría a doble espacio.
  defp lineas do
    @log
    |> File.stream!()
    |> Stream.map(&String.trim/1)
  end

  defp nivel(linea) do
    cond do
      String.contains?(linea, "ERROR") -> "ERROR"
      String.contains?(linea, "WARN") -> "WARN"
      true -> "INFO"
    end
  end
end

Reporte.main()
```

En `IO.puts(salida, linea)` el primer argumento es el **dispositivo**, y por eso la línea se escribe en el archivo abierto. Sin ese primer argumento, `IO.puts(linea)` escribiría en la consola. Y es **importante cerrar el archivo** con `File.close/1` al terminar, para liberar el recurso.

**¿Por qué aquí no se usa `case`?** Por esta línea:

```elixir
{:ok, salida} = File.open(@errores, [:write, :utf8])
```

Es una coincidencia directa, como la de la Versión 0, así que si `File.open/2` fallara el programa se detendría con un `MatchError`. Y está hecho **a propósito**, porque si no se puede crear el archivo de salida el programa no tiene nada útil que hacer. Es la filosofía de **"dejarlo fallar"**. Como regla práctica, use `case` o `with` cuando el error tenga una **respuesta razonable** (informar al usuario, usar un valor por defecto, continuar con otro archivo), y la coincidencia directa cuando el fallo signifique que el programa ya no tiene sentido.

> ⚠️ **Nota:** Olvidar invocar `File.close/1` es un error frecuente. Tenga en cuenta que siempre que se abra un archivo mediante `File.open/2`, este debe cerrarse explícitamente una vez finalice su uso, con el fin de liberar correctamente los recursos asociados.

Ejecute el script una vez más. Ahora se generan **dos archivos**. El primero, `errores.txt`:

```
=== Detalle de errores ===
2026-08-01 10:15:47 ERROR Fallo de conexion con la base de datos
2026-08-01 10:19:10 ERROR Timeout al consultar el servicio de pagos
2026-08-01 10:22:01 ERROR Fallo de conexion con la base de datos
```

Y el segundo, `resumen.txt`:

```
=== Eventos por nivel ===
ERROR: 3
INFO: 3
WARN: 1
```

Lo más importante de esta versión es que usa las dos formas de escribir, cada una donde corresponde. **Escriba de una sola vez lo que sepa que es pequeño y escriba poco a poco lo que pueda crecer sin límite.**

#### Un detalle de eficiencia

Esta solución recorre el log **dos veces**, una por cada archivo de salida. No consume más memoria, porque sigue procesando línea por línea, pero tarda el doble en leer. Si eso llegara a importar, ambas tareas podrían resolverse en una sola pasada usando `Enum.reduce/3` con un mapa como acumulador, a costa de un código bastante más denso. Es el intercambio habitual entre **legibilidad** y **rendimiento**; con dos pasadas sobre un archivo, casi siempre gana la legibilidad.

## Ejemplo 2: Anonimizar los registros antes de compartirlos

En el Ejemplo 1 el programa leía un archivo y producía otro distinto, un resumen. Este en cambio lo **transforma**, ya que la salida es una copia del original con las líneas modificadas. Y en su versión final tampoco procesará un archivo conocido de antemano, sino **todos los que encuentre** en la carpeta.

El equipo de soporte necesita enviarle los logs a un proveedor externo para que analice las fallas, pero por política de privacidad **no puede revelar los nombres de los usuarios**. Se requiere un programa que reemplace los nombres por `***` y deje las copias en una subcarpeta `publicos/`, conservando el nombre original de cada archivo.

Cree un archivo `anonimizador.exs` junto a los logs. Como en el Ejemplo 1, lo resolveremos en dos pasos, primero un solo archivo y después toda la carpeta.

### Versión 1: Transformar un archivo en otro

Empecemos por el caso simple, que es anonimizar únicamente `servidor.log` y dejar el resultado en `servidor_publico.log`.

```elixir
defmodule Anonimizador do
  @entrada Path.join(__DIR__, "servidor.log")
  @salida Path.join(__DIR__, "servidor_publico.log")

  def main do
    @entrada
    |> File.stream!()                                   # Lee línea por línea
    |> Stream.map(&ocultar_usuarios/1)                  # Transforma cada línea
    |> Enum.into(File.stream!(@salida, [:write]))       # Escribe línea por línea

    IO.puts("Anonimizado: #{@salida}")
  end

  defp ocultar_usuarios(linea) do
    String.replace(linea, ~r/Usuario \w+/, "Usuario ***")
  end
end

Anonimizador.main()
```

El contenido de `servidor_publico.log` queda así:

```
2026-08-01 10:15:02 INFO Usuario *** inicio sesion
2026-08-01 10:15:47 ERROR Fallo de conexion con la base de datos
2026-08-01 10:16:03 INFO Usuario *** inicio sesion
2026-08-01 10:18:22 WARN Memoria al 85 por ciento
2026-08-01 10:19:10 ERROR Timeout al consultar el servicio de pagos
2026-08-01 10:21:35 INFO Usuario *** cerro sesion
2026-08-01 10:22:01 ERROR Fallo de conexion con la base de datos
```

Las líneas de error y advertencia pasan intactas, ya que son justamente las que el proveedor necesita para diagnosticar.

Esta versión introduce dos cosas nuevas:

**1. Un stream también puede ser el destino de la escritura.** Hasta ahora usábamos `File.stream!/1` para leer. Al pasarlo a `Enum.into/2` con el modo `[:write]` se convierte en el **destino**, de manera que cada línea transformada se escribe de inmediato, sin acumular nada. Este es el modismo habitual para **convertir un archivo en otro**.

Compare este pipeline con el de la Versión 5 del Ejemplo 1. Allí abríamos el archivo con `File.open/2` y escribíamos con `IO.puts/2` porque queríamos escribir **solo algunas** líneas y con un encabezado propio. Aquí, en cambio, la salida es una línea por cada línea de entrada, y para ese caso `Enum.into/2` es mucho más directo.

**2. Las expresiones regulares.** `String.replace/3` acepta tanto un texto literal como una **expresión regular** para decidir qué reemplazar. En Elixir se escriben con el sigilo `~r/.../`:

```elixir
~r/Usuario \w+/
```

Esa expresión busca la palabra `Usuario`, seguida de un espacio, seguida de una o más letras o dígitos. Los símbolos más útiles son:

| Símbolo       | Significa                               | Ejemplo                                           |
| ------------- | --------------------------------------- | ------------------------------------------------- |
| `\w`          | Una letra, dígito o guion bajo          | `~r/\w+/` coincide con `ana`, `luis99`            |
| `\d`          | Un dígito                               | `~r/\d+/` coincide con `2026`, `85`               |
| `[[:punct:]]` | Un signo de puntuación                  | `~r/[[:punct:]]/` coincide con `.`, `,`, `!`, `¿` |
| `+`           | Uno o más del elemento anterior         | `\d+` coincide con `7` y con `12345`              |
| `*`           | Cero o más del elemento anterior        | `\s*` coincide también con la cadena vacía        |
| `.`           | Cualquier carácter                      | `~r/a.c/` coincide con `abc`, `a5c`               |

Para profundizar, consulte la [documentación del módulo Regex](https://hexdocs.pm/elixir/Regex.html).

### Versión 2: Procesar todos los archivos de la carpeta

**Nuevo requerimiento:** los logs no son uno solo. El servidor rota los archivos y en la carpeta hay varios, cuyos nombres no se conocen de antemano. El programa debe anonimizar **todos los `.log` que encuentre** y dejarlos en una subcarpeta `publicos/`.

Para probarlo, cree un segundo log llamado `respaldo.log` junto al que ya tiene:

```
2026-08-02 09:00:00 INFO Usuario marta inicio sesion
2026-08-02 09:05:10 WARN Disco al 90 por ciento
```

> ⚠️ **Antes de continuar:** borre el archivo `servidor_publico.log` que generó la Versión 1. Si no lo hace, el programa también lo procesará, porque termina en `.log` y el programa no tiene forma de distinguir un log original de una copia ya anonimizada.

```elixir
defmodule Anonimizador do
  @carpeta __DIR__
  @salida Path.join(__DIR__, "publicos")

  def main do
    File.mkdir_p!(@salida)   # Crea la carpeta destino si no existe

    @carpeta
    |> File.ls!()
    |> Enum.filter(&(Path.extname(&1) == ".log"))   # Solo los archivos .log
    |> Enum.sort()
    |> Enum.each(&anonimizar_archivo/1)
  end

  defp anonimizar_archivo(nombre) do
    entrada = Path.join(@carpeta, nombre)
    salida = Path.join(@salida, nombre)

    entrada
    |> File.stream!()                                  # Lee línea por línea
    |> Stream.map(&ocultar_usuarios/1)                 # Transforma cada línea
    |> Enum.into(File.stream!(salida, [:write]))       # Escribe línea por línea

    IO.puts("Anonimizado: #{nombre} -> publicos/#{nombre}")
  end

  defp ocultar_usuarios(linea) do
    String.replace(linea, ~r/Usuario \w+/, "Usuario ***")
  end
end

Anonimizador.main()
```

Al ejecutarlo:

```
Anonimizado: respaldo.log -> publicos/respaldo.log
Anonimizado: servidor.log -> publicos/servidor.log
```

Y `publicos/servidor.log` queda exactamente igual que el `servidor_publico.log` de la Versión 1.

El pipeline de transformación no cambió en absoluto. Es el mismo de la Versión 1, solo que ahora vive dentro de `anonimizar_archivo/1` y recibe las rutas como variables en lugar de leerlas de atributos. Lo único verdaderamente nuevo es cómo se **descubren** los archivos:

1. `File.ls!/1` **devuelve el contenido de una carpeta**, como una lista con los nombres de los archivos y subcarpetas que hay dentro. Es lo que permite trabajar sobre archivos que no se conocen de antemano. Devuelve solo los **nombres**, no las rutas completas; por eso hay que reconstruirlas con `Path.join/2`.

2. `Path.extname/1` **devuelve la extensión** de un archivo (`".log"`, `".txt"`), y con ella se filtra la lista para quedarse solo con los que interesan. Listar una carpeta y filtrar por extensión es un patrón muy frecuente.

3. `File.mkdir_p!/1` **crea la carpeta destino**, incluidos todos los directorios intermedios que hagan falta. Sin esa línea, la primera escritura fallaría porque `publicos/` no existe.

## Referencia rápida

Estas tablas reúnen, para consulta rápida durante los ejercicios, las funciones usadas en los ejemplos junto con unas pocas que le harán falta. **No es necesario memorizarlas**, lo importante es saber que existen. El resto está en la documentación oficial que se enlaza abajo.

### Leer y escribir

| Función          | Qué hace                                            | Devuelve                                 |
| ---------------- | --------------------------------------------------- | ---------------------------------------- |
| `File.read/1`    | Lee el archivo completo                             | `{:ok, contenido}` o `{:error, razón}`   |
| `File.read!/1`   | Igual, pero lanza excepción si falla                | El contenido directamente                |
| `File.write/2`   | Escribe (o sobrescribe) un archivo                  | `:ok` o `{:error, razón}`                |
| `File.write/3`   | Igual, recibiendo opciones (`[:append]`, `[:utf8]`) | `:ok` o `{:error, razón}`                |
| `File.stream!/1` | Crea un stream perezoso de líneas                   | Un stream                                |
| `File.open/2`    | Abre un archivo y devuelve un dispositivo           | `{:ok, dispositivo}` o `{:error, razón}` |
| `File.close/1`   | Cierra un archivo abierto                           | `:ok`                                    |

### Carpetas y rutas

| Función           | Qué hace                                                       | Ejemplo                                        |
| ----------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| `File.ls!/1`      | Lista los nombres del contenido de una carpeta                 | `File.ls!(".")` → `["servidor.log", …]`        |
| `File.mkdir_p/1`  | Crea la carpeta y todos los directorios intermedios que falten | `File.mkdir_p("publicos")` → `:ok`             |
| `Path.join/2`     | Une dos partes de una ruta con el separador del sistema        | `Path.join("/datos", "a.log")` → `"/datos/a.log"` |
| `Path.extname/1`  | Devuelve la extensión                                          | `Path.extname("servidor.log")` → `".log"`      |

### Ejercicio 0: Visor de archivos

### Ejercicio 1: Frecuencia de palabras

Cree un programa que:
1. Lea un archivo de texto
2. Cuente la frecuencia de cada palabra (ignorando mayúsculas y signos de puntuación)
3. Guarde los resultados en `frecuencia.txt` ordenados de mayor a menor frecuencia
4. El formato debe ser: `palabra: frecuencia`

**Ejemplo de entrada (`texto.txt`):**
```
Hola mundo. Hola Elixir!
Elixir es genial. Mundo, hola.
```

**Ejemplo de salida (`frecuencia.txt`):**
```
hola: 3
elixir: 2
mundo: 2
es: 1
genial: 1
```

Además, como paso intermedio, genere un archivo `texto_normalizado.txt` con el mismo texto de entrada pero **en minúsculas y sin signos de puntuación**, una línea por cada línea original. Constrúyalo con el modismo de streams de la Versión 1 del Ejemplo 2:

```elixir
File.stream!(entrada)
|> Stream.map(&normalizar/1)
|> Enum.into(File.stream!(salida, [:write]))
```

**Pistas:**
- Use `String.downcase/1` para normalizar todas las palabras a minúsculas
- Para eliminar los signos de puntuación use `String.replace/3` con la expresión regular vista en el Ejemplo 2: `String.replace(linea, ~r/[[:punct:]]/u, "")`
- Use `String.split/1` para separar palabras, por defecto separa por espacios
- Use `Enum.frequencies/1` para contar la frecuencia de cada palabra
- Use `Enum.sort_by/3` con `:desc` para ordenar de mayor a menor frecuencia
- Al escribir con `Enum.into/2`, recuerde que cada línea debe terminar en `\n`; si le aplicó `String.trim/1`, tendrá que volver a agregarlo

### Ejercicio 2: Procesamiento de datos de un CSV

Dado el archivo `productos.csv`:

nombre,precio,cantidad
Laptop,1200,10
Mouse,25,50
Teclado,75,30
Monitor,300,15

Cree un módulo que:
1. Lea el archivo `productos.csv`
2. Convierta cada línea en un mapa: `%{nombre: "Laptop", precio: 1200, cantidad: 10}`
3. Calcule el valor total del inventario (suma de `precio * cantidad`)
4. Encuentre el producto más caro y el más barato
5. Genere un reporte en `inventario.txt` con:
   - Valor total del inventario
   - Producto más caro
   - Producto más barato

**Pistas:**

### Ejercicio 3: Procesamiento por lotes

Cuando un archivo tiene millones de líneas, a veces conviene procesarlo **en bloques** en lugar de línea por línea, por ejemplo para enviar los registros a un servicio externo de cien en cien, o para mostrar el avance al usuario cada cierto número de líneas.

Escriba un módulo `ProcesadorLotes` que:

1. Genere, con una función propia, el archivo de prueba `ventas.txt` con **1000 líneas**. Resuélvalo como prefiera; si lo desea, también puede pedirle el archivo a una IA generativa como ChatGPT en lugar de programarlo.
2. Lea ese archivo con `File.stream!/1` y lo agrupe en lotes de **100 líneas** usando `Stream.chunk_every/2`.
3. Por cada lote, imprima el número de lote, cuántas líneas trae y la **suma de los valores** de ese lote.
4. Al final, imprima el total general y verifique que coincide con la suma de los subtotales.

**Formato de `ventas.txt`.** Cada línea es `venta_N;valor`, separados por punto y coma, donde `N` es el consecutivo de la venta (de 1 a 1000) y `valor` un número entero aleatorio entre 1000 y 50000. El archivo **no lleva encabezado**:

```
venta_1;24817
venta_2;3502
venta_3;48190
...
venta_1000;15744
```

**Formato esperado de la salida:**
```
Lote 1: 100 líneas, subtotal 2543120
Lote 2: 100 líneas, subtotal 2611874
...
Lote 10: 100 líneas, subtotal 2498003
Total general: 25430118
```

**Pistas:**
- Recuerde aplicar `String.trim/1` antes de separar cada línea con `String.split/2`
- Use `Enum.with_index/2` para numerar los lotes
- `Stream.chunk_every/2` funciona igual que `Enum.chunk_every/2`, pero de forma perezosa, así que nunca hay más de un lote en memoria

Responda además: ¿qué ventaja tiene procesar por lotes frente a procesar línea por línea? ¿Y frente a cargar el archivo completo?

**Punto opcional: separador de miles.** Los números grandes se leen mejor como `2.543.120` que como `2543120`. Elixir **no trae** una función para eso en su librería estándar, así que hay que escribirla. Implemente una función `formatear/1` que inserte un punto cada tres dígitos, contando desde la derecha.

*Pista:* la clave es **invertir la cadena**, agrupar de a tres con `Enum.chunk_every/2` y volver a invertir. Se resuelve encadenando funciones que ya conoce, como `Integer.to_string/1`, `String.reverse/1`, `String.graphemes/1`, `Enum.chunk_every/2` y `Enum.join/2`.

```elixir
formatear(2543120)   # => "2.543.120"
formatear(999)       # => "999"
formatear(1000)      # => "1.000"
```

### Ejercicio 4: Pokédex con persistencia

Extienda el proyecto de la Pokédex desarrollado en la guía de structs para que haga lo siguiente:

1. Guardar todos los Pokémon en `pokedex.csv` con el formato CSV
2. Formato de cada Pokémon: `numero,nombre,nivel,movimiento1;movimiento2;movimiento3`
3. Cargar los datos al iniciar el programa
4. Guardar automáticamente después de cada operación que modifique los datos (registrar, liberar, actualizar Pokémon o sus movimientos)

**Ejemplo de `pokedex.csv`:**
```
numero,nombre,nivel,movimientos
25,Pikachu,12,Impactrueno;Ataque Rapido;Cola Ferrea
6,Charizard,36,Lanzallamas;Garra Dragon
9,Blastoise,34,Hidrobomba;Rayo Burbuja;Proteccion
```

Tenga en cuenta que el archivo tiene **dos separadores distintos**. La coma separa los campos del Pokémon y el punto y coma separa los movimientos dentro del último campo. Al cargar hay que deshacer los dos niveles; al guardar, construirlos.

**Funciones requeridas:**

Se recomienda crear un módulo `Archivo` con funciones como:

- `Archivo.guardar_pokemones/1`: Guarda la colección de Pokémon en `pokedex.csv`
- `Archivo.cargar_pokemones/0`: Carga los Pokémon desde `pokedex.csv`
- Modificar el módulo principal de la Pokédex para llamar a estas funciones en los momentos adecuados (al iniciar y después de cada cambio).

Tenga en cuenta lo siguiente:

- **La primera línea es un encabezado y no es un Pokémon.** Descártela al cargar con `Stream.drop(1)`, como en el Ejercicio 2, y vuelva a escribirla al guardar.
- **Tenga en cuenta el primer arranque**, cuando `pokedex.csv` todavía no existe. `File.read/1` devolverá `{:error, :enoent}` y `cargar_pokemones/0` debe responder con una colección vacía, no reventar.
- **El nivel se guarda como texto.** Al cargar hay que convertirlo de nuevo a número con `String.to_integer/1`, de lo contrario los cálculos de estadísticas fallarán.
- Recuerde que los Pokémon se guardan en un **mapa indexado por el número de Pokédex**. Para escribirlos necesitará recorrer sus valores (`Map.values/1`), y al cargar, reconstruir el mapa.
- Como la Pokédex no mantiene estado en memoria entre llamadas, cada función que modifique los datos debe devolver la colección actualizada y `main` encargarse de persistirla. Mantenga `Archivo` como el **único módulo con efectos secundarios**, tal como se hizo con `guardar/2` en el Ejemplo 1.

# Manejo de archivos

El manejo de archivos en Elixir se realiza principalmente a través de tres módulos: `File`, `IO` y `Path`. Estos módulos permiten leer y escribir archivos, así como crear y recorrer carpetas. Algunas de estas operaciones pueden fallar, por lo que, como se ha visto en las guías anteriores, su resultado se indica mediante una tupla que contiene el resultado de la operación o el motivo del error. 

En esta guía se abordarán los siguientes temas:

* Lectura de archivos con `File.read/1` y manejo del resultado con tuplas.
* Escritura de archivos con `File.write/2` y sus opciones.
* Construcción de rutas portables con el módulo `Path` y `__DIR__`.
* Lectura perezosa de archivos grandes con `File.stream!/1`.
* Transformación de un archivo en otro mediante streams.
* Operaciones con carpetas: listar, filtrar y crear.

## Ejemplo 1: Analizador de registros del servidor

Un **servidor** es un computador que permanece encendido prestando un servicio a otros equipos, como el que aloja la página web de la universidad. Nadie está sentado frente a él, así que escribe todo lo que hace en un archivo de texto llamado **log** (registro). Cada vez que ocurre algo relevante **agrega una línea al final** con la fecha, la hora, un **nivel de severidad** y una descripción. Si el sistema se cae de madrugada, la causa está ahí.

Los tres niveles más comunes son `INFO` (algo normal ocurrió), `WARN` (una advertencia) y `ERROR` (algo falló). Como el servidor no para, estos archivos **crecen sin límite** y pueden pesar varios gigabytes, así que revisarlos a mano es inviable.

El equipo de soporte de una empresa necesita una herramienta para analizar ese log, pero **no la pide toda de una vez**. Como en un proyecto real, cada versión traerá un requerimiento nuevo que obligará a mejorar la solución, empezando por lo mínimo.

Primero, cree un archivo `servidor.log` con el siguiente contenido para trabajar. El formato de cada línea es *fecha, hora, nivel y descripción*.

```
2026-08-01 10:15:02 INFO Usuario carlos inicio sesion
2026-08-01 10:15:47 ERROR Fallo de conexion con la base de datos
2026-08-01 10:16:03 INFO Usuario luis inicio sesion
2026-08-01 10:18:22 WARN Memoria al 85 por ciento
2026-08-01 10:19:10 ERROR Timeout al consultar el servicio de pagos
2026-08-01 10:21:35 INFO Usuario carlos cerro sesion
2026-08-01 10:22:01 ERROR Fallo de conexion con la base de datos
```

Junto a ese archivo, cree otro llamado `reporte.exs`, donde iremos escribiendo el programa. **Después de cada versión, ejecútelo** desde la terminal para comprobar el resultado:

```bash
elixir reporte.exs
```

### Versión 1: Ver qué hay dentro del archivo

El primer reto es **abrir el archivo y mostrarlo en pantalla**. Para eso basta `File.read/1`, que recibe la ruta del archivo y devuelve su contenido completo como una cadena de texto.

```elixir
defmodule Reporte do
  def main do
    {:ok, contenido} = File.read("servidor.log")
    IO.puts(contenido)
  end
end

Reporte.main()
```

Al ejecutarlo verá el log completo impreso en la consola.

`File.read/1` devuelve una tupla con la convención `{:ok, valor}` / `{:error, motivo}`, y el operador `=` la descompone con coincidencia de patrones, enlazando el texto a la variable `contenido`.

**Ahora provoque el error.** Cambie el nombre del archivo por uno que no exista y vuelva a ejecutar:

```elixir
{:ok, contenido} = File.read("no_existe.log")
```

El programa se detiene con este mensaje:

```
** (MatchError) no match of right hand side value:

    {:error, :enoent}
```

Es un `MatchError`. El patrón de la izquierda exige un `:ok`, la función devolvió `{:error, :enoent}` y las formas no coinciden. Ahí está el problema que debe resolver la siguiente versión, porque un archivo puede no existir y el programa tiene que **manejar ese caso** en lugar de reventar.

### Versión 2: Contar las líneas y manejar el error

**Primer requerimiento:** contar cuántas líneas tiene el log y cuántos errores contiene. Además, a partir de lo que acabamos de ver, se deben manejar los dos resultados posibles de `File.read/1` con un `case` en lugar de una coincidencia directa:

```elixir
defmodule Reporte do
  def main do
    analizar("servidor.log")
    analizar("no_existe.log")   # Para comprobar el manejo de errores
  end

  defp analizar(ruta) do
    case File.read(ruta) do
      {:ok, contenido} ->
        # Dividir el contenido en líneas (\n)
        lineas = String.split(contenido, "\n", trim: true)
        # Contar cuántas líneas tienen nivel ERROR
        errores = Enum.count(lineas, fn linea -> nivel(linea) == "ERROR" end)

        IO.puts("Líneas totales: #{length(lineas)}")
        IO.puts("Errores encontrados: #{errores}")

      {:error, :enoent} ->
        IO.puts("Error: el archivo no existe")

      {:error, razon} ->
        IO.puts("Error al leer el archivo: #{razon}")
    end
  end

  # El nivel de severidad es la tercera palabra de la línea, después de la fecha y la hora
  defp nivel(linea) do
    linea
    |> String.split()
    |> Enum.at(2)
  end
end

Reporte.main()
```

Al ejecutar `elixir reporte.exs` debería ver:

```
Líneas totales: 7
Errores encontrados: 3
Error: el archivo no existe
```

Dos detalles del código:

- En `String.split(contenido, "\n", trim: true)`, la opción `trim: true` descarta las cadenas vacías; sin ella, el salto de línea final del archivo produciría una última línea vacía y el conteo saldría en 8.
- En `nivel/1`, `String.split/1` divide por espacios cuando no recibe un segundo argumento, y `Enum.at/2` cuenta las posiciones desde 0, así que la posición 2 es la tercera palabra. Por ejemplo, en la línea `2026-08-01 10:15:47 ERROR Fallo de conexion con la base de datos`, la fecha queda en la posición 0, la hora en la 1 y `ERROR` en la 2.

Compare este resultado con la Versión 1. **La segunda llamada, con un archivo inexistente, ya no revienta el programa**, sino que informa el error y continúa. Esa es la ventaja de que `File.read/1` devuelva una tupla en vez de lanzar una excepción, ya que el fallo termina siendo un valor más, que se maneja con las mismas herramientas que cualquier otro dato.

El átomo que acompaña a `{:error, razon}` indica qué salió mal. Además de `:enoent` (el archivo no existe), uno frecuente es `:eisdir`, que aparece cuando la ruta es una carpeta y no un archivo.

> ⚠️ **Nota:** casi toda función de `File` tiene una variante con `!` (`File.read!/1`, `File.write!/2`, …) que **lanza una excepción** en lugar de devolver una tupla.

### Versión 3: Guardar el reporte en un archivo

**Nuevo requerimiento:** el resultado no puede quedarse en la pantalla. Debe guardarse en un archivo `reporte.txt`, para poder adjuntarlo al informe semanal del área.

La versión anterior no lo permite, porque `analizar/1` calcula los totales y los imprime en el mismo lugar. Para enviar el resultado a un archivo hay que **separar responsabilidades**:

- `generar_texto/1` construye el texto del reporte.
- `guardar/2` lo escribe en el archivo.
- `analizar/2` ya no imprime, sino que devuelve una tupla `{:ok, mensaje}` o `{:error, razon}`.
- `mostrar_resultado/1` es la única función que imprime, con una cláusula por cada forma de la tupla.

```elixir
defmodule Reporte do
  def main do
    analizar("servidor.log", "reporte.txt")
    |> mostrar_resultado()
  end

  defp analizar(ruta_log, ruta_reporte) do
    case File.read(ruta_log) do
      {:ok, contenido} ->
        contenido
        |> generar_texto()
        |> guardar(ruta_reporte)

      {:error, razon} ->
        {:error, razon}
    end
  end

  # Función pura: recibe el contenido y devuelve el texto del reporte
  defp generar_texto(contenido) do
    lineas = String.split(contenido, "\n", trim: true)
    errores = Enum.count(lineas, fn linea -> nivel(linea) == "ERROR" end)

    """
    === Reporte del log ===
    Líneas totales: #{length(lineas)}
    Errores encontrados: #{errores}
    """
  end

  # El nivel de severidad es la tercera palabra de la línea, después de la fecha y la hora
  defp nivel(linea) do
    linea
    |> String.split()
    |> Enum.at(2)
  end

  # Efecto secundario aislado: escribir en disco
  defp guardar(texto, ruta) do
    case File.write(ruta, texto) do
      :ok -> {:ok, "Reporte generado en #{ruta}"}
      {:error, razon} -> {:error, razon}
    end
  end

  defp mostrar_resultado({:ok, mensaje}), do: IO.puts(mensaje)
  defp mostrar_resultado({:error, razon}), do: IO.puts("Error: #{razon}")
end

Reporte.main()
```

Ejecute el programa. En la consola solo verá `Reporte generado en reporte.txt`, pero **junto a su script aparecerá un archivo nuevo**, `reporte.txt`, con este contenido:

```
=== Reporte del log ===
Líneas totales: 7
Errores encontrados: 3
```

Algunos detalles del código:

- El `"""` (*heredoc*) permite escribir un texto de varias líneas sin tener que concatenar `\n` a mano.
- `File.write/2` devuelve solo `:ok` cuando todo sale bien, sin tupla, porque no hay ningún valor que entregar. Por eso `guardar/2` arma su propia tupla `{:ok, mensaje}`, para que `mostrar_resultado/1` reciba siempre la misma forma.
- `mostrar_resultado/1` tiene **una sola cláusula de error**. La distinción de `{:error, :enoent}` que hacía la Versión 2 ya no hace falta, porque el átomo viaja dentro de la tupla y `{:error, razon}` lo imprime tal cual, sea un error de lectura o de escritura. Distinguir un código específico solo vale la pena cuando se quiere dar un mensaje distinto para ese caso.

**Opciones de escritura.** `File.write/2` **sobrescribe** el archivo. Si en lugar de eso quisiéramos ir acumulando reportes, se usa la opción `:append`:

```elixir
# Agregar al final sin sobrescribir
File.write("historico.txt", "Nueva entrada\n", [:append])
```

### Versión 4: Rutas que no dependan de dónde se ejecute

**Nuevo requerimiento:** el análisis se ejecutará de forma automática cada noche mediante una tarea programada del sistema, que invoca el script desde otra carpeta. El programa debe funcionar sin importar desde dónde se ejecute.

Y aquí aparece un problema, ya que el programa anterior funciona **solo si se ejecuta desde la carpeta donde está el log**. Si se ejecuta `elixir carpeta/reporte.exs` desde otra carpeta, `File.read("servidor.log")` falla con `:enoent`, porque la ruta es relativa a la carpeta actual de la terminal y no a la del script.

La solución es construir las rutas a partir de `__DIR__`, que siempre apunta a la carpeta del archivo `.exs`, y unirlas con `Path.join/2`, que es preferible a concatenar con `<>` porque usa el separador de cada sistema operativo, `/` en Linux y macOS y `\` en Windows.

En el archivo de la Versión 3, agregue los dos atributos al inicio del módulo y cambie `main`:

```elixir
defmodule Reporte do
  @log Path.join(__DIR__, "servidor.log")
  @salida Path.join(__DIR__, "reporte.txt")

  def main do
    analizar(@log, @salida)
    |> mostrar_resultado()
  end

  # analizar/2, generar_texto/1, nivel/1, guardar/2 y mostrar_resultado/1 quedan tal como estaban
end
```

Ese es todo el cambio. Como las responsabilidades ya estaban separadas, construir las rutas de otra forma no obliga a tocar las funciones que leen el log y arman el reporte.

Hasta ahora los **atributos de módulo** guardaban valores literales (`@minimo 1`). Aquí guardan el resultado de una expresión, `Path.join(__DIR__, "servidor.log")`, que Elixir calcula una sola vez al compilar.

Ahora el programa se puede ejecutar desde cualquier carpeta. **Compruébelo:** sitúese en otro directorio y ejecute el script indicando su ruta completa. Antes fallaba con `:enoent`; ahora funciona igual.

```bash
cd ..
elixir carpeta_del_proyecto/reporte.exs
```

El mensaje de la consola ahora muestra la ruta completa del reporte, por ejemplo `Reporte generado en /home/usuario/proyecto/reporte.txt`, porque `@salida` ya no es solo un nombre de archivo, sino la ruta construida con `__DIR__`.

### Versión 5: Contar los eventos de cada nivel

**Nuevo requerimiento:** el reporte se queda corto. Ahora quieren saber **cuántos eventos hay de cada tipo** (`INFO`, `WARN`, `ERROR`), no solo cuántos errores.

Contar cuántos elementos hay de cada grupo es justo lo que hace `Enum.frequencies_by/2`. En el archivo de la Versión 4, agregue la función `contar_por_nivel/1` como paso nuevo del pipeline de `analizar/2` y cambie `generar_texto/1` para que reciba el conteo:

```elixir
defmodule Reporte do
  # Los atributos, main/0, nivel/1, guardar/2 y mostrar_resultado/1 quedan tal como estaban

  defp analizar(ruta_log, ruta_reporte) do
    case File.read(ruta_log) do
      {:ok, contenido} ->
        contenido
        |> contar_por_nivel()   # Paso nuevo
        |> generar_texto()
        |> guardar(ruta_reporte)

      {:error, razon} ->
        {:error, razon}
    end
  end

  defp contar_por_nivel(contenido) do
    contenido
    |> String.split("\n", trim: true)
    |> Enum.frequencies_by(&nivel/1)   # Cuenta cuántas hay de cada nivel
  end

  defp generar_texto(conteo) do
    lineas =
      conteo
      |> Enum.map(fn {nivel, cantidad} -> "#{nivel}: #{cantidad}" end)
      |> Enum.join("\n")

    """
    === Eventos por nivel ===
    #{lineas}
    """
  end
end
```

El contenido de `reporte.txt` queda así:

```
=== Eventos por nivel ===
ERROR: 3
INFO: 3
WARN: 1
```

`generar_texto/1` **tuvo que reescribirse**, porque al cambiar el requerimiento del reporte dejó de recibir el contenido crudo del archivo y ahora recibe un mapa con el conteo (`%{"ERROR" => 3, "INFO" => 3, "WARN" => 1}`).

En `contar_por_nivel/1` aparece una **captura**, `&nivel/1`, que referencia una función privada del módulo actual sin necesidad de nombrarlo.

### Versión 6: Cuando el log es demasiado grande

**Nuevo requerimiento:** el programa va a correr sobre el log real del servidor, que pesa **varios gigabytes**.

Esto rompe la solución actual, ya que `File.read/1` carga **todo el archivo en memoria**. Con un log de prueba de 7 líneas no hay problema, pero con uno de varios gigabytes el programa se quedaría sin memoria antes de empezar a contar.

Aquí entra `File.stream!/1`, que aplica a un archivo la **evaluación perezosa** de los streams. En lugar de devolver el contenido, devuelve un stream que produce las líneas una por una. Solo cuando una función de `Enum` empieza a consumirlo, el stream va leyendo del disco la línea que le piden, la entrega y pasa a la siguiente.

El siguiente diagrama muestra el impacto en la memoria de `File.read/1` frente a `File.stream!/1`:

![Diagrama de memoria](res/file_read_vs_stream.svg)

En el archivo de la Versión 5, cambie `analizar/2` y `contar_por_nivel/1`:

```elixir
defmodule Reporte do
  # Los atributos, main/0, generar_texto/1, nivel/1, guardar/2 y mostrar_resultado/1 quedan tal como estaban

  defp analizar(ruta_log, ruta_reporte) do
    if File.exists?(ruta_log) do
      ruta_log
      |> contar_por_nivel()
      |> generar_texto()
      |> guardar(ruta_reporte)
    else
      {:error, :enoent}
    end
  end

  defp contar_por_nivel(ruta) do
    ruta
    |> File.stream!()                  # Produce las líneas una por una
    |> Enum.frequencies_by(&nivel/1)   # Cuenta cuántas hay de cada nivel
  end
end
```

El contenido de `reporte.txt` es el mismo de la Versión 5. El cambio principal está en `contar_por_nivel/1`, que ahora recibe la ruta en lugar del contenido. `File.stream!/1` ocupa el lugar de `String.split/3`, porque el stream ya entrega el archivo separado en líneas, y `Enum.frequencies_by/2` lo consume igual que antes consumía la lista. Cada línea del stream conserva su salto de línea final, pero eso no afecta a `nivel/1`, porque `String.split/1` lo descarta.

`analizar/2` ya no puede usar `case` sobre el resultado de la lectura, porque `File.stream!/1` termina en `!` y no tiene una variante que devuelva una tupla. Si el log no existe, lanza una excepción y el programa se detiene. Por eso `analizar/2` comprueba primero con `File.exists?/1` que el log exista y, si no, devuelve `{:error, :enoent}`, la misma tupla que antes entregaba `File.read/1`, de modo que `mostrar_resultado/1` no necesita cambios. Esta verificación cubre el caso más frecuente; otros fallos, como la falta de permisos de lectura, seguirían produciendo una excepción.

## Ejemplo 2: Anonimizar los registros antes de compartirlos

En el Ejemplo 1 el programa leía un archivo y producía otro distinto, un resumen. Este en cambio lo **transforma**, ya que la salida es una copia del original con las líneas modificadas. Y en su versión final tampoco procesará un archivo conocido de antemano, sino **todos los que encuentre** en la carpeta.

El equipo de soporte necesita enviarle los logs a un proveedor externo para que analice las fallas, pero por política de privacidad **no puede revelar los nombres de los usuarios**. Se requiere un programa que reemplace los nombres por `***` y deje las copias en una subcarpeta `publicos/`, conservando el nombre original de cada archivo.

Cree un archivo `anonimizador.exs` junto a los logs. Lo resolveremos en dos pasos, primero un solo archivo y después toda la carpeta.

### Versión 1: Transformar un archivo en otro

Empecemos por el caso simple, que es anonimizar únicamente `servidor.log` y dejar el resultado en `servidor_publico.log`.

```elixir
defmodule Anonimizador do
  @entrada Path.join(__DIR__, "servidor.log")
  @salida Path.join(__DIR__, "servidor_publico.log")

  def main do
    @entrada
    |> anonimizar(@salida)
    |> mostrar_resultado()
  end

  defp anonimizar(entrada, salida) do
    if File.exists?(entrada) do
      entrada
      |> File.stream!()                                  # Lee línea por línea
      |> Stream.map(&ocultar_usuarios/1)                 # Transforma cada línea
      |> Enum.into(File.stream!(salida, [:write]))       # Escribe línea por línea

      :ok
    else
      {:error, "el archivo no existe"}
    end
  end

  defp ocultar_usuarios(linea) do
    String.replace(linea, ~r/Usuario \w+/, "Usuario ***")
  end

  defp mostrar_resultado(:ok), do: IO.puts("Anonimizado: #{@salida}")
  defp mostrar_resultado({:error, motivo}), do: IO.puts("Error: #{motivo}")
end

Anonimizador.main()
```

El contenido de `servidor_publico.log` queda así:

```
2026-08-01 10:15:02 INFO Usuario *** inicio sesion
2026-08-01 10:15:47 ERROR Fallo de conexion con la base de datos
2026-08-01 10:16:03 INFO Usuario *** inicio sesion
2026-08-01 10:18:22 WARN Memoria al 85 por ciento
2026-08-01 10:19:10 ERROR Timeout al consultar el servicio de pagos
2026-08-01 10:21:35 INFO Usuario *** cerro sesion
2026-08-01 10:22:01 ERROR Fallo de conexion con la base de datos
```

Las líneas de error y advertencia pasan intactas, ya que son las que el proveedor necesita para diagnosticar.

`anonimizar/2` comprueba con `File.exists?/1` que el archivo exista antes de leerlo, igual que `analizar/2` en la Versión 6 del Ejemplo 1. Además, esta versión introduce dos cosas nuevas:

**1. Un stream también puede ser el destino de la escritura.** Hasta ahora usábamos `File.stream!/1` para leer. Al pasarlo a `Enum.into/2` con el modo `[:write]` se convierte en el **destino**, de manera que cada línea transformada se escribe de inmediato, sin acumular nada. Esta es la forma habitual en Elixir de **convertir un archivo en otro**.

**2. Las expresiones regulares.** `String.replace/3` acepta tanto un texto literal como una **expresión regular** para decidir qué reemplazar. En Elixir se escriben entre `~r/` y `/`:

```elixir
~r/Usuario \w+/
```

Esa expresión busca la palabra `Usuario`, seguida de un espacio, seguida de una o más letras o dígitos (`\w+`). Las expresiones regulares son un tema amplio, y para conocer más símbolos puede consultar la [documentación del módulo Regex](https://hexdocs.pm/elixir/Regex.html).

### Versión 2: Procesar todos los archivos de la carpeta

**Nuevo requerimiento:** los logs no son uno solo. El servidor rota los archivos y en la carpeta hay varios, cuyos nombres no se conocen de antemano. El programa debe anonimizar **todos los `.log` que encuentre** y dejarlos en una subcarpeta `publicos/`.

Para probarlo, cree un segundo log llamado `respaldo.log` junto al que ya tiene:

```
2026-08-02 09:00:00 INFO Usuario marta inicio sesion
2026-08-02 09:05:10 WARN Disco al 90 por ciento
```

> ⚠️ **Antes de continuar:** borre el archivo `servidor_publico.log` que generó la Versión 1. Si no lo hace, el programa también lo procesará, porque termina en `.log` y el programa no tiene forma de distinguir un log original de una copia ya anonimizada.

En el archivo de la Versión 1, reemplace los atributos por `@carpeta` y `@salida`, cambie `main`, agregue `anonimizar_carpeta/1`, `listar_logs/1` y `anonimizar_archivo/1`, y reemplace `mostrar_resultado/1` por `mostrar_resultado/2`:

```elixir
defmodule Anonimizador do
  @carpeta __DIR__
  @salida Path.join(__DIR__, "publicos")

  def main do
    case File.mkdir_p(@salida) do   # Crea la carpeta destino si no existe
      :ok -> anonimizar_carpeta(@carpeta)
      {:error, razon} -> IO.puts("No se pudo crear la carpeta publicos: #{razon}")
    end
  end

  defp anonimizar_carpeta(carpeta) do
    carpeta
    |> listar_logs()
    |> Enum.each(&anonimizar_archivo/1)
  end

  defp listar_logs(carpeta) do
    carpeta
    |> File.ls!()
    |> Enum.filter(&(Path.extname(&1) == ".log"))   # Solo los archivos .log
    |> Enum.sort()
  end

  defp anonimizar_archivo(nombre) do
    @carpeta
    |> Path.join(nombre)
    |> anonimizar(Path.join(@salida, nombre))
    |> mostrar_resultado(nombre)
  end

  defp mostrar_resultado(:ok, nombre), do: IO.puts("Anonimizado: #{nombre} -> publicos/#{nombre}")
  defp mostrar_resultado({:error, motivo}, nombre), do: IO.puts("No se pudo anonimizar #{nombre}: #{motivo}")

  # anonimizar/2 y ocultar_usuarios/1 quedan tal como estaban
end
```

Al ejecutarlo:

```
Anonimizado: respaldo.log -> publicos/respaldo.log
Anonimizado: servidor.log -> publicos/servidor.log
```

Y `publicos/servidor.log` queda exactamente igual que el `servidor_publico.log` de la Versión 1.

`anonimizar/2` se reutiliza sin cambios. Como ya recibía las rutas como argumentos, `anonimizar_archivo/1` solo construye la ruta de entrada y la de salida de cada archivo y la llama. `mostrar_resultado/2` recibe además el nombre del archivo, para indicar cuál falló.

Lo nuevo es cómo se **descubren** los archivos, que es la tarea de `listar_logs/1`, y la creación de la carpeta de destino en `main`:

1. `File.ls!/1` **devuelve el contenido de una carpeta**, como una lista con los nombres de los archivos y subcarpetas que hay dentro. Es lo que permite trabajar sobre archivos que no se conocen de antemano. Devuelve solo los **nombres**, no las rutas completas; por eso hay que reconstruirlas con `Path.join/2`. Aquí se usa la variante con `!` porque la carpeta que se lista es la del propio script, que siempre existe.

2. `Path.extname/1` **devuelve la extensión** de un archivo (`".log"`, `".txt"`). Listar una carpeta y filtrar por extensión es un patrón muy frecuente.

3. `File.mkdir_p/1` crea la carpeta `publicos/`, y también las carpetas intermedias que falten en la ruta. Si la carpeta ya existe, no hace nada. Devuelve `:ok` o `{:error, razon}`, y por eso `main` solo procesa la carpeta cuando la creación salió bien. Si no se puede crear el destino, no tiene sentido intentar anonimizar ningún archivo.

## Referencia rápida

Estas tablas reúnen, para consulta rápida durante los ejercicios, las funciones usadas en los ejemplos junto con unas pocas que le harán falta. **No es necesario memorizarlas**, lo importante es saber que existen. El resto está en la documentación oficial que se enlaza abajo.

### Leer y escribir

| Función          | Qué hace                                            | Devuelve                               |
| ---------------- | --------------------------------------------------- | -------------------------------------- |
| `File.read/1`    | Lee el archivo completo                             | `{:ok, contenido}` o `{:error, razón}` |
| `File.read!/1`   | Igual, pero lanza excepción si falla                | El contenido directamente              |
| `File.write/2`   | Escribe (o sobrescribe) un archivo                  | `:ok` o `{:error, razón}`              |
| `File.write/3`   | Igual, recibiendo opciones (`[:append]`, `[:utf8]`) | `:ok` o `{:error, razón}`              |
| `File.stream!/1` | Crea un stream perezoso de líneas                   | Un stream                              |
| `File.open/2`    | Abre un archivo para lectura/escritura              | `{:ok, io_device}` o `{:error, razón}` |

### Carpetas y rutas

| Función          | Qué hace                                                       | Ejemplo                                           |
| ---------------- | -------------------------------------------------------------- | ------------------------------------------------- |
| `File.exists?/1` | Indica si la ruta existe, sea archivo o carpeta                | `File.exists?("servidor.log")` → `true`           |
| `File.ls!/1`     | Lista los nombres del contenido de una carpeta                 | `File.ls!(".")` → `["servidor.log", …]`           |
| `File.mkdir_p/1` | Crea la carpeta y todos los directorios intermedios que falten | `File.mkdir_p("publicos")` → `:ok`                |
| `Path.join/2`    | Une dos partes de una ruta con el separador del sistema        | `Path.join("/datos", "a.log")` → `"/datos/a.log"` |
| `Path.extname/1` | Devuelve la extensión                                          | `Path.extname("servidor.log")` → `".log"`         |

## Ejercicios propuestos

Realice los siguientes ejercicios para practicar el manejo de archivos en Elixir. Están ordenados de menor a mayor dificultad, así que **empiece por el Ejercicio 0**, que sirve de calentamiento.

### Ejercicio 0: Visor de archivos

Escriba un módulo `Visor` que solicite al usuario la ruta de un archivo y muestre su contenido en pantalla:

1. Pida la ruta con `IO.gets/1` y recuerde aplicarle `String.trim/1`.
2. Si el archivo existe, imprima su contenido y, al final, cuántas líneas tiene.
3. Si no existe, imprima `"El archivo <ruta> no existe"`.
4. Si la ruta corresponde a una **carpeta** y no a un archivo, imprima `"<ruta> es una carpeta, no un archivo"`.

Pruébelo con `servidor.log`, con un nombre inventado y con la carpeta `publicos`.

Tenga en cuenta lo siguiente:

- Organice la solución con una función `main` que delegue en funciones pequeñas.
- Maneje los tres casos con `case` sobre el resultado de `File.read/1`, teniendo en cuenta que el error de una carpeta llega como `{:error, :eisdir}`.

### Ejercicio 1: Frecuencia de palabras

Cree un programa que:
1. Lea un archivo de texto
2. Cuente la frecuencia de cada palabra (ignorando mayúsculas y signos de puntuación)
3. Guarde los resultados en `frecuencia.txt` ordenados de mayor a menor frecuencia
4. El formato debe ser: `palabra: frecuencia`

**Ejemplo de entrada (`texto.txt`):**
```
Hola mundo. Hola Elixir!
Elixir es genial. Mundo, hola.
```

**Ejemplo de salida (`frecuencia.txt`):**
```
hola: 3
elixir: 2
mundo: 2
es: 1
genial: 1
```

Además, como paso intermedio, genere un archivo `texto_normalizado.txt` con el mismo texto de entrada pero **en minúsculas y sin signos de puntuación**, una línea por cada línea original. Constrúyalo con streams, como en la Versión 1 del Ejemplo 2:

```elixir
File.stream!(entrada)
|> Stream.map(&normalizar/1)
|> Enum.into(File.stream!(salida, [:write]))
```

**Pistas:**
- Use `String.downcase/1` para normalizar todas las palabras a minúsculas
- Para eliminar los signos de puntuación use `String.replace/3` con una expresión regular, `String.replace(linea, ~r/[[:punct:]]/u, "")`, donde `[[:punct:]]` representa cualquier signo de puntuación
- Use `String.split/1` para separar palabras, por defecto separa por espacios
- Use `Enum.frequencies/1` para contar la frecuencia de cada palabra
- Use `Enum.sort_by/3` con `:desc` para ordenar de mayor a menor frecuencia
- Al escribir con `Enum.into/2`, recuerde que cada línea debe terminar en `\n`; si le aplicó `String.trim/1`, tendrá que volver a agregarlo

### Ejercicio 2: Procesamiento de datos de un CSV

Dado el archivo `productos.csv`:

```csv
nombre,precio,cantidad
Laptop,1200,10
Mouse,25,50
Teclado,75,30
Monitor,300,15
```

Cree un módulo que:
1. Lea el archivo `productos.csv`
2. Convierta cada línea en un mapa: `%{nombre: "Laptop", precio: 1200, cantidad: 10}`
3. Calcule el valor total del inventario (suma de `precio * cantidad`)
4. Encuentre el producto más caro y el más barato
5. Genere un reporte en `inventario.txt` con:
   - Valor total del inventario
   - Producto más caro
   - Producto más barato
   - Lista de productos ordenados por valor en inventario

**Pistas:**
- Use `File.stream!/1` y `Stream.drop(1)` para saltar el encabezado
- Aplique `String.trim/1` a cada línea antes de separarla. Si no lo hace, el último campo llegará como `"10\n"` y `String.to_integer/1` fallará con un `ArgumentError`
- Use `String.split/2` y `String.to_integer/1`
- Use `Enum.reduce/3` para calcular totales
- Use `Enum.max_by/2` y `Enum.min_by/2`

### Ejercicio 3: Procesamiento por lotes

Cuando un archivo tiene millones de líneas, a veces conviene procesarlo **en bloques** en lugar de línea por línea, por ejemplo para enviar los registros a un servicio externo de cien en cien, o para mostrar el avance al usuario cada cierto número de líneas.

Escriba un módulo `ProcesadorLotes` que:

1. Genere, con una función propia, el archivo de prueba `ventas.txt` con **1000 líneas**. Resuélvalo como prefiera; si lo desea, también puede pedirle el archivo a una IA generativa como ChatGPT en lugar de programarlo.
2. Lea ese archivo con `File.stream!/1` y lo agrupe en lotes de **100 líneas** usando `Stream.chunk_every/2`.
3. Por cada lote, imprima el número de lote, cuántas líneas trae y la **suma de los valores** de ese lote.
4. Al final, imprima el total general y verifique que coincide con la suma de los subtotales.

**Formato de `ventas.txt`.** Cada línea es `venta_N;valor`, separados por punto y coma, donde `N` es el consecutivo de la venta (de 1 a 1000) y `valor` un número entero aleatorio entre 1000 y 50000. El archivo **no lleva encabezado**:

```
venta_1;24817
venta_2;3502
venta_3;48190
...
venta_1000;15744
```

**Formato esperado de la salida:**
```
Lote 1: 100 líneas, subtotal 2543120
Lote 2: 100 líneas, subtotal 2611874
...
Lote 10: 100 líneas, subtotal 2498003
Total general: 25430118
```

**Pistas:**
- Recuerde aplicar `String.trim/1` antes de separar cada línea con `String.split/2`
- Use `Enum.with_index/2` para numerar los lotes
- `Stream.chunk_every/2` funciona igual que `Enum.chunk_every/2`, pero de forma perezosa, así que nunca hay más de un lote en memoria

Responda además: ¿qué ventaja tiene procesar por lotes frente a procesar línea por línea? ¿Y frente a cargar el archivo completo?

### Ejercicio 4: Pokédex con persistencia

Extienda el proyecto de la Pokédex desarrollado en la guía de structs para que haga lo siguiente:

1. Guardar todos los Pokémon en `pokedex.csv` con el formato CSV
2. Formato de cada Pokémon: `numero,nombre,nivel,movimiento1;movimiento2;movimiento3`
3. Cargar los datos al iniciar el programa
4. Guardar automáticamente después de cada operación que modifique los datos (registrar, liberar, actualizar Pokémon o sus movimientos)

**Ejemplo de `pokedex.csv`:**
```
numero,nombre,nivel,movimientos
25,Pikachu,12,Impactrueno;Ataque Rapido;Cola Ferrea
6,Charizard,36,Lanzallamas;Garra Dragon
9,Blastoise,34,Hidrobomba;Rayo Burbuja;Proteccion
```

Tenga en cuenta que el archivo tiene **dos separadores distintos**. La coma separa los campos del Pokémon y el punto y coma separa los movimientos dentro del último campo. Al cargar hay que deshacer los dos niveles; al guardar, construirlos.

**Funciones requeridas:**

Se recomienda crear un módulo `Archivo` con funciones como:

- `Archivo.guardar_pokemones/1`: Guarda la colección de Pokémon en `pokedex.csv`
- `Archivo.cargar_pokemones/0`: Carga los Pokémon desde `pokedex.csv`
- Modificar el módulo principal de la Pokédex para llamar a estas funciones en los momentos adecuados (al iniciar y después de cada cambio).

Tenga en cuenta lo siguiente:

- **La primera línea es un encabezado y no es un Pokémon.** Descártela al cargar con `Stream.drop(1)`, como en el Ejercicio 2, y vuelva a escribirla al guardar.
- **Tenga en cuenta el primer arranque**, cuando `pokedex.csv` todavía no existe. Compruébelo con `File.exists?/1` antes de leerlo, como en los ejemplos, y en ese caso `cargar_pokemones/0` debe responder con una colección vacía, no reventar.
- **El nivel se guarda como texto.** Al cargar hay que convertirlo de nuevo a número con `String.to_integer/1`, de lo contrario los cálculos de estadísticas fallarán.
- Recuerde que los Pokémon se guardan en un **mapa indexado por el número de Pokédex**. Para escribirlos necesitará recorrer sus valores (`Map.values/1`), y al cargar, reconstruir el mapa.
- Las funciones de la Pokédex no almacenan los datos, ya que cada una recibe el mapa y devuelve uno nuevo. Por esta razón, `main` debe tomar el mapa actualizado que devuelve cada función y pasarlo a `Archivo.guardar_pokemones/1`. Mantenga `Archivo` como el **único módulo con efectos secundarios**, tal como se hizo con `guardar/2` en el Ejemplo 1.

# Guards y manejo de resultados

En la guía anterior se estudiaron los operadores, las estructuras de decisión (`if`, `cond` y `case`) y una primera aproximación a la coincidencia de patrones. En esta guía se profundiza en esos conceptos para resolver un problema muy frecuente: **qué hacer cuando una operación puede fallar**.

Los temas que se abordarán son:

- Uso de *guards* (`when`) para seleccionar cláusulas de función.
- Atributos de módulo como constantes.
- Uso de tuplas `{:ok, valor}` y `{:error, motivo}` para representar resultados.
- La estructura `with` para encadenar operaciones que pueden fallar.
- Criterios para elegir entre `if`, `cond`, `case`, *guards* y `with`.

> ⚠️ **Importante:** los ejemplos de esta guía utilizan el módulo `Util` construido en la guía anterior. Asegúrese de tener el archivo `util.exs` compilado con `elixirc` en la misma carpeta donde ejecute los scripts.

## Ejemplo 1

Se requiere un programa que simule una lotería básica, donde el usuario puede elegir un número entre **1 y 10**, luego el programa debe generar un número aleatorio en el mismo rango, determinar si el usuario ganó o no y cuál fue la diferencia. Si el usuario escribe un número fuera de este rango, el programa debe informarle que su elección es inválida y terminar.

Para generar números aleatorios en Elixir, se puede utilizar el módulo `:rand` de Erlang. Para más información, puede consultar la [documentación oficial](https://www.erlang.org/doc/apps/stdlib/rand.html).

### Versión 1


```elixir
defmodule Loteria do
  @minimo 1
  @maximo 10

  def main do
    "Ingrese un número entre #{@minimo} y #{@maximo}: "
    |> Util.leer(:integer)
    |> jugar()
    |> Util.imprimir_mensaje()
  end

  defp jugar(numero) when numero >= @minimo and numero <= @maximo do
    numero
    |> calcular_diferencia()
    |> evaluar_resultado()
  end

  defp jugar(_), do: "Número no válido, fin del juego."

  defp calcular_diferencia(numero_usuario) do 
    numero_ganador = :rand.uniform(@maximo) # Genera un número aleatorio entre 1 y @maximo
    abs(numero_usuario - numero_ganador) # Devuelve el valor absoluto de la diferencia
  end

  defp evaluar_resultado(0), do: "¡Felicidades, has ganado!"
  defp evaluar_resultado(diferencia), do: "Lo siento, has perdido. La diferencia fue de #{diferencia}."
end

Loteria.main()
```

Guarde el archivo como `loteria.exs` y ejecútelo con `elixir loteria.exs`. Al escribir un número dentro del rango, la sesión se ve así (lo que aparece después de los dos puntos es lo que usted escribe):

```
Ingrese un número entre 1 y 10: 7
Lo siento, has perdido. La diferencia fue de 2.
```

Como el número ganador se genera al azar, el resultado cambia en cada ejecución. Vuelva a correrlo varias veces hasta que le salga `¡Felicidades, has ganado!`.

Ahora pruebe con un número fuera del rango:

```
Ingrese un número entre 1 y 10: 15
Número no válido, fin del juego.
```

Ese segundo caso lo atiende la cláusula `jugar(_)`, ya que el *guard* de la primera no se cumple.

En esta implementación se usan dos **atributos de módulo**, `@minimo` y `@maximo`, para definir el rango de números válidos. La forma `@nombre valor` crea una **constante que se resuelve al compilar**, así que el valor queda incrustado en el código generado y no cambia durante la ejecución. Ajustar el rango más adelante solo exige tocarlo en un lugar.

Que se resuelva al compilar es también lo que permite usar `@minimo` dentro del *guard*, porque cuando el programa corre ahí ya no hay un atributo sino el número `1`. Un *guard* no admitiría, en cambio, una llamada a una función del módulo.

Dos detalles más de este ejemplo:

- `:rand` es un **módulo de Erlang**, no de Elixir; por eso su nombre empieza con dos puntos. Es un ejemplo concreto de la interoperabilidad entre ambos lenguajes, ya que cualquier librería de Erlang puede usarse directamente desde Elixir.
- `:rand.uniform/1` es una **función impura** porque para la misma entrada devuelve resultados distintos en cada llamada. La impureza queda aislada en `calcular_diferencia/1`, mientras que `evaluar_resultado/1` permanece pura y, por lo tanto, es fácil de probar.


### Versión 2 (opcional)

La función `jugar/1` también puede escribirse de la siguiente manera:

```elixir
defp jugar(numero) when numero in @minimo..@maximo do
  numero
  |> calcular_diferencia()
  |> evaluar_resultado()
end
```

La diferencia es que se utiliza un rango de valores (`@minimo..@maximo`) en lugar de combinar operaciones de comparación con `and`. El uso de rangos en los `guard` es una práctica idiomática en Elixir que puede ser mejor en ciertos casos.

## Ejemplo 2

Se requiere un programa que calcule las operaciones aritméticas básicas a partir de dos números ingresados por el usuario. Se debe validar que en la división no se produzca una división por cero, cuando una operación se pueda hacer debe retornar un `:ok` junto a la respuesta, en caso contrario debe retornar `:error` con un mensaje apropiado.

```elixir
defmodule Calculadora do

  def main do
    numero1 = Util.leer("Ingrese el primer número: ", :integer)
    numero2 = Util.leer("Ingrese el segundo número: ", :integer)
    operacion = Util.leer("Escriba 1 para suma, 2 para resta, 3 para multiplicación, 4 para división: ", :integer)

    validar_operacion(numero1, numero2, operacion)
    |> generar_mensaje()
    |> Util.imprimir_mensaje()
  end

  defp validar_operacion(numero1, numero2, operacion) when operacion in 1..4 do
    operar(numero1, numero2, operacion)
  end

  defp validar_operacion(_, _, _), do: {:error, "Operación no válida."}

  defp operar(numero1, numero2, 1), do: {:ok, numero1 + numero2}
  defp operar(numero1, numero2, 2), do: {:ok, numero1 - numero2}
  defp operar(numero1, numero2, 3), do: {:ok, numero1 * numero2}
  defp operar(_numero1, 0, 4), do: {:error, "División por cero no permitida."}
  defp operar(numero1, numero2, 4), do: {:ok, numero1 / numero2}

  defp generar_mensaje({:ok, resultado}), do: "El resultado es: #{resultado}"
  defp generar_mensaje({:error, mensaje}), do: "Error: #{mensaje}"

end

Calculadora.main()
```

Al ejecutarlo, cada camino del código produce una salida distinta. Una división normal:

```
Ingrese el primer número: 10
Ingrese el segundo número: 4
Escriba 1 para suma, 2 para resta, 3 para multiplicación, 4 para división: 4
El resultado es: 2.5
```

Una división por cero:

```
Ingrese el primer número: 10
Ingrese el segundo número: 0
Escriba 1 para suma, 2 para resta, 3 para multiplicación, 4 para división: 4
Error: División por cero no permitida.
```

Y una operación que no existe:

```
Ingrese el primer número: 10
Ingrese el segundo número: 4
Escriba 1 para suma, 2 para resta, 3 para multiplicación, 4 para división: 9
Error: Operación no válida.
```

Pruebe los tres casos antes de seguir leyendo e identifique qué cláusula produjo cada mensaje.

Se destaca la utilización de **tuplas** para manejar los resultados de las operaciones, lo que permite un manejo de errores más claro y conciso. Además, gracias al **pattern matching**, se puede descomponer fácilmente el resultado en varias partes y actuar en consecuencia. Lea el código e intente identificar cómo se manejan los diferentes casos.

En la cláusula `operar(_numero1, 0, 4)`, el `0` del patrón hace que coincida **solo cuando el segundo número es `0`**, detectando la división por cero antes de realizarla. Combinar variables con valores concretos (`0`, `:ok`, `:error`) en un mismo patrón es una de las ideas más potentes del pattern matching.

También importa **el orden de las cláusulas**. La de división por cero debe ir *antes* que `operar(numero1, numero2, 4)`, porque Elixir evalúa de arriba hacia abajo y ejecuta la primera que coincida. Si estuvieran al revés, la división por cero nunca se detectaría.

Además, `operar/3` no necesita una cláusula final que capture "cualquier otro caso", ya que el *guard* `when operacion in 1..4` de `validar_operacion/3` garantiza que solo lleguen los valores 1, 2, 3 y 4, y todos están cubiertos. Agregar una cláusula inalcanzable sería código muerto, y contradice la filosofía de **"dejarlo fallar"**. Si llegara un valor imposible, es preferible que el programa falle de forma evidente a que lo oculte.

## Ejemplo 3

Una plataforma necesita validar los datos de registro de un nuevo usuario. La validación debe realizarse en orden: el nombre no puede estar vacío, la edad debe ser un número válido y mayor o igual a 18, y el correo debe contener el carácter "@". Si todas las validaciones son correctas, se debe registrar al usuario; si alguna falla, se debe informar el motivo del error.

### Versión 1

```elixir
defmodule Registro do

  def main do
    nombre = Util.leer("Ingrese el nombre: ", :string)
    edad = Util.leer("Ingrese la edad: ", :string)
    email = Util.leer("Ingrese el email: ", :string)

    resultado =
      with {:ok, nombre} <- validar_nombre(nombre),
           {:ok, edad} <- validar_edad(edad),
           {:ok, email} <- validar_email(email) do
        {:ok, "Usuario #{nombre} (#{edad} años, #{email}) registrado correctamente."}
      end

    generar_mensaje(resultado)
    |> Util.imprimir_mensaje()
  end

  defp validar_nombre(""), do: {:error, "El nombre no puede estar vacío."}
  defp validar_nombre(nombre), do: {:ok, nombre}

  defp validar_edad(edad) do
    case Integer.parse(edad) do
      {numero, _} when numero >= 18 -> {:ok, numero}
      {_numero, _} -> {:error, "El usuario debe ser mayor de edad."}
      :error -> {:error, "La edad no es un número válido."}
    end
  end

  defp validar_email(email) do
    if String.contains?(email, "@") do
      {:ok, email}
    else
      {:error, "El email debe contener el carácter '@'."}
    end
  end

  defp generar_mensaje({:ok, mensaje}), do: mensaje
  defp generar_mensaje({:error, motivo}), do: "Error de registro: #{motivo}"

end

Registro.main()
```

Con datos válidos:

```
Ingrese el nombre: Carlos
Ingrese la edad: 32
Ingrese el email: caflorez@uniquindio.edu.co
Usuario Carlos (32 años, caflorez@uniquindio.edu.co) registrado correctamente.
```

Si la edad no llega a 18:

```
Ingrese el nombre: Ana
Ingrese la edad: 15
Ingrese el email: ana@uqvirtual.edu.co
Error de registro: El usuario debe ser mayor de edad.
```

Ahora haga fallar **las tres validaciones a la vez**, con el nombre vacío, una edad de 15 y un correo sin arroba:

```
Ingrese el nombre:
Ingrese la edad: 15
Ingrese el email: ana.correo.com
Error de registro: El nombre no puede estar vacío.
```

Solo se reporta el primer error, aunque los tres datos estén mal. Eso es lo que hace la estructura `with`, que encadena varias operaciones que pueden fallar y ejecuta su cuerpo únicamente si **todas** tienen éxito.

- Cada línea usa el operador `<-`, que intenta hacer **pattern matching** entre el patrón de la izquierda (`{:ok, valor}`) y el resultado de la derecha.
- Si **todos** los patrones coinciden, se ejecuta el bloque `do` y se construye el mensaje de éxito.
- Si **alguno no coincide**, `with` **detiene la ejecución** y devuelve ese valor sin ejecutar el cuerpo. Por eso `generar_mensaje/1` recibe la tupla de error y muestra el motivo correspondiente.

Sin `with`, cada validación obligaría a anidar un `case` o `if` dentro del anterior. Aquí las tres quedan una debajo de la otra, y por eso resulta la estructura indicada para funciones que retornan `{:ok, valor}` o `{:error, motivo}`.

> ⚠️ **Importante:** En `validar_edad/1`, el *guard* `when numero >= 18` acompaña a un patrón de `case`. Además de las cabezas de función (Ejemplo 1), los guards también pueden usarse dentro de un `case`.

### Versión 2

Se puede agregar un bloque `else` al `with` para manejar de forma explícita los valores que no coincidieron. Así, el manejo del error queda dentro del propio `with` y ya no es necesaria la función `generar_mensaje/1`:

```elixir
def main do
  nombre = Util.leer("Ingrese el nombre: ", :string)
  edad = Util.leer("Ingrese la edad: ", :string)
  email = Util.leer("Ingrese el email: ", :string)

  with {:ok, nombre} <- validar_nombre(nombre),
       {:ok, edad} <- validar_edad(edad),
       {:ok, email} <- validar_email(email) do
    "Usuario #{nombre} (#{edad} años, #{email}) registrado correctamente."
  else
    {:error, motivo} -> "Error de registro: #{motivo}"
  end
  |> Util.imprimir_mensaje()
end
```

La salida es idéntica a la de la Versión 1 en todos los casos. El cambio es de organización, no de comportamiento, porque el manejo del error pasó a vivir dentro del propio `with`.

> ⚠️ **Importante:** `with` es una de las construcciones más usadas en Elixir para manejar flujos donde varias operaciones consecutivas pueden fallar, como validaciones encadenadas o la lectura de varios recursos.

## ¿Cuándo usar cada estructura?

A lo largo de la guía se presentaron varias estructuras de control y de decisión. La siguiente tabla resume cuándo conviene usar cada una:

| Estructura | Úsela cuando... |
| --- | --- |
| `if` | Hay **una sola** condición booleana. |
| `cond` | Hay **varias condiciones independientes** y se ejecuta la primera que resulte verdadera. |
| `case` | Se compara **un mismo valor** contra varios **patrones** (pattern matching). |
| `guard` (`when`) | Se quiere elegir la **cláusula de una función** (o de un `case`) según condiciones sobre los argumentos. |
| `with` | Se **encadenan varias operaciones que pueden fallar** y solo interesa continuar si **todas** tienen éxito. |

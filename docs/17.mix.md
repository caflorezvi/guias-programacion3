# Mix

Hasta ahora, cada programa ha sido un script `.exs` que se ejecuta con `elixir`. Este enfoque es adecuado para programas de uno o dos archivos, pero a medida que el código crece presenta algunas limitaciones:

- Para reutilizar el módulo `Util` fue necesario compilarlo manualmente con `elixirc` y ubicar el archivo `.beam` en la carpeta de cada script, además de recompilarlo cada vez que `util.exs` cambiaba.
- En el chat fue necesario indicar a `iex`, uno por uno, los archivos que debía cargar.
- Las pruebas se realizaron manualmente, ejecutando el programa y revisando la salida.

**Mix** es la herramienta oficial de construcción y gestión de proyectos de Elixir, y resuelve estas limitaciones. Es el equivalente a herramientas como `npm` en JavaScript o `Maven` en Java.

## ¿Qué hace Mix?

- **Estructura del proyecto.** Todos los proyectos Mix siguen la misma organización de carpetas, lo que facilita ubicar el código fuente y las pruebas.
- **Compilación.** `mix compile` compila todos los archivos de `lib/`, sin importar cuántos sean ni las dependencias entre ellos, y solo recompila los que cambiaron.
- **Pruebas.** `mix test` ejecuta todas las pruebas del proyecto e informa cuáles fallaron.
- **Gestión de dependencias.** Para usar una librería externa basta con declararla en `mix.exs` y ejecutar `mix deps.get`. Las librerías de Elixir se publican en [Hex](https://hex.pm).

Para más información, puede consultar la [documentación oficial de Mix](https://hexdocs.pm/mix/Mix.html).

## Comandos comunes de Mix

Estos son los comandos que se usarán en la guía:

```bash
mix new banco           # Crea un proyecto nuevo llamado banco
mix compile             # Compila el proyecto
iex -S mix              # Abre IEx con el proyecto compilado y cargado
mix test                # Ejecuta las pruebas
mix run                 # Ejecuta la aplicación
mix deps.get            # Descarga las dependencias declaradas en mix.exs
mix help                # Muestra la ayuda de todos los comandos
```

## Ejemplo: Las cuentas de un banco

Un banco necesita un sistema para manejar las cuentas de sus clientes: abrir una cuenta, consignar, retirar y consultar el saldo. Lo construiremos como un proyecto Mix, y en cada versión el proyecto crecerá con una de las herramientas que ofrece Mix.

### Versión 1: Crear el proyecto y la lógica de una cuenta

En la terminal, cree el proyecto y entre a su carpeta:

```bash
mix new banco
cd banco
```

Abra la carpeta `banco` en Visual Studio Code. `mix new` creó esta estructura:

```
banco/
├── lib/                  # Código fuente del proyecto
│   └── banco.ex          # Un módulo Banco de ejemplo
├── test/                 # Pruebas
│   ├── test_helper.exs   # Inicia ExUnit antes de las pruebas
│   └── banco_test.exs    # Pruebas del módulo de ejemplo
├── .formatter.exs        # Configuración del formateador de código
├── .gitignore            # Archivos que Git debe ignorar
├── mix.exs               # Configuración del proyecto
└── README.md             # Descripción del proyecto
```

Al compilar aparece además la carpeta `_build/`, con los archivos `.beam`. No hace falta tocarla, y ya está incluida en `.gitignore`.

El archivo `mix.exs` es la configuración principal del proyecto. Allí se indican su nombre y versión, la versión de Elixir que necesita y las librerías externas que usa. De forma resumida, se ve así:

```elixir
defmodule Banco.MixProject do
  use Mix.Project # Indica que este módulo es un proyecto Mix

  # Configuración del proyecto
  def project do
    [
      app: :banco,
      version: "0.1.0",
      elixir: "~> 1.18",
      start_permanent: Mix.env() == :prod,
      deps: deps()
    ]
  end

  # Configuración de la aplicación
  def application do
    [
      extra_applications: [:logger]
    ]
  end

  # Librerías externas que usa el proyecto
  defp deps do
    []
  end
end
```

`:logger` es la librería estándar de Elixir para registrar mensajes (*logging*), y `extra_applications` indica que el proyecto la usa.

La primera pieza del banco es la lógica de una cuenta: cómo cambia el saldo al consignar o retirar. Cree el archivo `lib/cuenta.ex`:

```elixir
defmodule Cuenta do
  @moduledoc """
  Operaciones sobre el saldo de una cuenta.
  Son funciones puras: reciben un saldo y devuelven el nuevo, sin guardar nada.
  """

  def depositar(saldo, monto) when monto > 0, do: {:ok, saldo + monto}
  def depositar(_saldo, _monto), do: {:error, :monto_invalido}

  def retirar(_saldo, monto) when monto <= 0, do: {:error, :monto_invalido}
  def retirar(saldo, monto) when monto > saldo, do: {:error, :saldo_insuficiente}
  def retirar(saldo, monto), do: {:ok, saldo - monto}
end
```

En la terminal, ubicado en la carpeta `banco` (la que contiene `mix.exs`), abra IEx con el proyecto cargado:

```bash
iex -S mix
```

Si lo ejecuta desde otra carpeta, Mix no encuentra el proyecto y muestra el error `"mix" with no arguments must be executed in a directory with a mix.exs file`. Puede usar la terminal integrada de Visual Studio Code, que se abre en la carpeta del proyecto.

Mix compila todos los archivos de `lib/` y los deja disponibles en IEx, sin `elixirc` y sin indicar los archivos uno por uno:

```elixir
iex> Cuenta.depositar(100, 50)
{:ok, 150}
iex> Cuenta.retirar(100, 150)
{:error, :saldo_insuficiente}
```

Si modifica un archivo mientras IEx está abierto, escriba `recompile()` para cargar los cambios sin salir.

### Versión 2: Probar la cuenta con ExUnit

Hasta ahora, la única forma de saber si el código funcionaba era ejecutarlo y revisar la salida. **ExUnit**, el framework de pruebas de Elixir, permite escribir esas revisiones como código y repetirlas todas con un solo comando.

Las pruebas se ubican en la carpeta `test`, en archivos cuyo nombre termina en `_test.exs`. Cree el archivo `test/cuenta_test.exs`:

```elixir
defmodule CuentaTest do
  use ExUnit.Case # Importa las funcionalidades de ExUnit para pruebas

  describe "depositar/2" do
    test "aumenta el saldo" do
      assert Cuenta.depositar(100, 50) == {:ok, 150}
    end

    test "no acepta montos negativos ni cero" do
      assert Cuenta.depositar(100, -50) == {:error, :monto_invalido}
      assert Cuenta.depositar(100, 0) == {:error, :monto_invalido}
    end
  end

  describe "retirar/2" do
    test "disminuye el saldo" do
      assert Cuenta.retirar(100, 30) == {:ok, 70}
    end

    test "no permite retirar más que el saldo" do
      assert Cuenta.retirar(100, 150) == {:error, :saldo_insuficiente}
    end

    test "no acepta montos negativos ni cero" do
      assert Cuenta.retirar(100, -10) == {:error, :monto_invalido}
    end
  end
end
```

Toda prueba se define dentro de un módulo que usa `ExUnit.Case`. La función `test` define una prueba, y dentro de ella `assert` verifica que una condición se cumpla. `describe` agrupa las pruebas de una misma función, y su nombre aparece en el reporte cuando una de ellas falla.

Ejecute las pruebas:

```bash
mix test
```

```
.......
Finished in 0.01 seconds (0.00s async, 0.01s sync)

Result: 7 passed (1 doctest, 6 tests)
```

Cada punto es una prueba que pasó. Son siete porque `mix test` también ejecuta `test/banco_test.exs`, el archivo de ejemplo que creó `mix new`.

Para ver cómo se reporta un error, cambie en la primera prueba el valor esperado por `{:ok, 160}` y ejecute de nuevo:

```
  1) test depositar/2 aumenta el saldo (CuentaTest)
     test/cuenta_test.exs:5
     Assertion with == failed
     code:  assert Cuenta.depositar(100, 50) == {:ok, 160}
     left:  {:ok, 150}
     right: {:ok, 160}
```

ExUnit indica qué prueba falló, en qué línea, y los dos valores que comparó: `left` es lo que devolvió la función y `right` lo que se esperaba. Vuelva a dejar el valor en `{:ok, 150}`.

Además de `assert`, estas son las aserciones más usadas:

- `refute expresion`: la prueba pasa si la expresión es falsa.
- `assert_raise TipoError, fn -> ... end`: verifica que el código lance una excepción del tipo indicado.
- `assert_in_delta valor1, valor2, delta`: verifica que dos números estén dentro de un margen, útil para comparar flotantes.

### Versión 3: El banco como proceso

`Cuenta` calcula saldos, pero no los recuerda. El banco necesita guardar el saldo de cada cuenta entre una operación y otra, y para eso se usa un `GenServer`, como en la guía de OTP. Reemplace el contenido de `lib/banco.ex` por:

```elixir
defmodule Banco do
  use GenServer

  # --- Funciones del cliente ---

  def start_link(_opts) do
    GenServer.start_link(__MODULE__, %{}, name: __MODULE__)
  end

  def abrir(numero), do: GenServer.call(__MODULE__, {:abrir, numero})
  def saldo(numero), do: GenServer.call(__MODULE__, {:saldo, numero})
  def depositar(numero, monto), do: GenServer.call(__MODULE__, {:depositar, numero, monto})
  def retirar(numero, monto), do: GenServer.call(__MODULE__, {:retirar, numero, monto})

  # --- Callbacks del servidor ---

  # El estado es un mapa que asocia cada número de cuenta con su saldo
  @impl true
  def init(cuentas), do: {:ok, cuentas}

  @impl true
  def handle_call({:abrir, numero}, _from, cuentas) do
    if Map.has_key?(cuentas, numero) do
      {:reply, {:error, :cuenta_existe}, cuentas}
    else
      {:reply, :ok, Map.put(cuentas, numero, 0)}
    end
  end

  def handle_call({:saldo, numero}, _from, cuentas) do
    case Map.fetch(cuentas, numero) do
      {:ok, saldo} -> {:reply, {:ok, saldo}, cuentas}
      :error -> {:reply, {:error, :cuenta_no_existe}, cuentas}
    end
  end

  def handle_call({:depositar, numero, monto}, _from, cuentas) do
    operar(cuentas, numero, &Cuenta.depositar(&1, monto))
  end

  def handle_call({:retirar, numero, monto}, _from, cuentas) do
    operar(cuentas, numero, &Cuenta.retirar(&1, monto))
  end

  # Aplica al saldo una operación de Cuenta y guarda el nuevo saldo si salió bien
  defp operar(cuentas, numero, operacion) do
    case Map.fetch(cuentas, numero) do
      :error ->
        {:reply, {:error, :cuenta_no_existe}, cuentas}

      {:ok, saldo} ->
        case operacion.(saldo) do
          {:ok, nuevo_saldo} -> {:reply, {:ok, nuevo_saldo}, Map.put(cuentas, numero, nuevo_saldo)}
          {:error, razon} -> {:reply, {:error, razon}, cuentas}
        end
    end
  end
end
```

`Banco` no sabe cómo se calcula un depósito o un retiro. Solo guarda los saldos y le pide a `Cuenta` que haga el cálculo, pasándole la operación como una función anónima. Así, las reglas de las cuentas siguen siendo funciones puras, y las pruebas de la Versión 2 siguen sirviendo sin cambios.

Como `banco.ex` ya no tiene la función de ejemplo `Banco.hello/0`, borre el archivo `test/banco_test.exs`, o sus pruebas fallarán.

Abra IEx con `iex -S mix`, inicie el banco y pruébelo:

```elixir
iex> Banco.start_link([])
{:ok, #PID<0.149.0>}
iex> Banco.abrir("001")
:ok
iex> Banco.depositar("001", 200)
{:ok, 200}
iex> Banco.retirar("001", 500)
{:error, :saldo_insuficiente}
iex> Banco.retirar("001", 50)
{:ok, 150}
iex> Banco.saldo("999")
{:error, :cuenta_no_existe}
```

### Versión 4: Iniciar el banco con la aplicación

La versión anterior tiene dos problemas. Cada vez que se abre IEx hay que acordarse de iniciar el banco con `Banco.start_link([])`. Y si el proceso falla, nadie lo vuelve a iniciar.

En la guía de supervisores, el supervisor se iniciaba desde `main`. En un proyecto Mix no hay `main`. En su lugar, el proyecto define una **aplicación**, un módulo que usa `Application` y cuya función `start/2` Elixir llama al iniciar el proyecto. Lo habitual es que esa función inicie un **supervisor raíz** con los procesos del sistema.

Cree el archivo `lib/banco/application.ex`:

```elixir
defmodule Banco.Application do
  use Application # Indica que este módulo es una aplicación OTP

  @impl true
  def start(_type, _args) do
    hijos = [
      Banco # Equivale a {Banco, []}: el supervisor llama a Banco.start_link([])
    ]

    # El supervisor raíz vigila a todos los procesos del banco
    Supervisor.start_link(hijos, strategy: :one_for_one, name: Banco.Supervisor)
  end
end
```

Para que Elixir sepa cuál es el módulo de la aplicación, agregue la opción `mod` a la función `application` de `mix.exs`:

```elixir
def application do
  [
    mod: {Banco.Application, []}, # Módulo que inicia la aplicación
    extra_applications: [:logger]
  ]
end
```

Abra de nuevo `iex -S mix`. Ahora el banco ya está corriendo, sin iniciarlo a mano:

```elixir
iex> Banco.abrir("001")
:ok
iex> Banco.depositar("001", 200)
{:ok, 200}
iex> Process.exit(Process.whereis(Banco), :kill)
true
iex> Banco.saldo("001")
{:error, :cuenta_no_existe}
```

Después de terminar el proceso a la fuerza, el banco sigue respondiendo porque el supervisor lo reinició. Pero la cuenta `"001"` ya no existe, ya que el proceso nuevo empezó con el estado inicial, un mapa vacío. Es el mismo comportamiento que tenía la caja registradora en la guía de supervisores.

Con la aplicación también funciona `mix run`, que la inicia y termina en cuanto `start/2` acaba, porque no hay nada más que ejecutar. Para trabajar con el banco, use `iex -S mix`.

#### Las pruebas del banco

Cree el archivo `test/banco_test.exs` con estas dos pruebas:

```elixir
defmodule BancoTest do
  use ExUnit.Case

  test "una cuenta nueva empieza en 0" do
    assert Banco.abrir("001") == :ok
    assert Banco.saldo("001") == {:ok, 0}
  end

  test "depositar aumenta el saldo" do
    Banco.abrir("001")
    assert Banco.depositar("001", 200) == {:ok, 200}
  end
end
```

Ejecute `mix test` varias veces. Algunas veces todo pasa, y otras falla la primera prueba:

```
  1) test una cuenta nueva empieza en 0 (BancoTest)
     left:  {:error, :cuenta_existe}
     right: :ok
```

Hay dos razones. Primero, `mix test` inicia la aplicación antes de las pruebas, así que todas usan **el mismo proceso `Banco`**. Segundo, ExUnit ejecuta las pruebas en **orden aleatorio**. Cuando la prueba del depósito se ejecuta primero, ya abrió la cuenta `"001"`, y la otra prueba no puede abrirla de nuevo. Una prueba que pasa o falla según el orden no sirve, porque no indica si el código está bien.

La solución es que cada prueba trabaje con su propia cuenta. El bloque `setup` se ejecuta **antes de cada prueba**, y lo que devuelve llega a la prueba en un mapa llamado *contexto*. Reemplace el contenido de `test/banco_test.exs` por:

```elixir
defmodule BancoTest do
  use ExUnit.Case

  # Antes de cada prueba se abre una cuenta con un número que no se repite
  setup do
    numero = "cuenta-#{System.unique_integer([:positive])}"
    :ok = Banco.abrir(numero)
    {:ok, numero: numero} # El número se entrega a la prueba en el contexto
  end

  test "una cuenta nueva empieza en 0", %{numero: numero} do
    assert Banco.saldo(numero) == {:ok, 0}
  end

  test "no se puede abrir dos veces la misma cuenta", %{numero: numero} do
    assert Banco.abrir(numero) == {:error, :cuenta_existe}
  end

  test "depositar y retirar actualizan el saldo", %{numero: numero} do
    assert Banco.depositar(numero, 200) == {:ok, 200}
    assert Banco.retirar(numero, 50) == {:ok, 150}
    assert Banco.saldo(numero) == {:ok, 150}
  end

  test "un retiro rechazado no cambia el saldo", %{numero: numero} do
    Banco.depositar(numero, 100)
    assert Banco.retirar(numero, 500) == {:error, :saldo_insuficiente}
    assert Banco.saldo(numero) == {:ok, 100}
  end

  test "no se puede operar una cuenta que no existe" do
    assert Banco.depositar("no-existe", 100) == {:error, :cuenta_no_existe}
  end
end
```

`System.unique_integer/1` devuelve un número distinto cada vez que se llama, así que ninguna prueba toca la cuenta de otra. Ahora `mix test` pasa siempre, sin importar el orden:

```
Result: 10 passed
```

> ⚠️ **Pruebas concurrentes:** con `use ExUnit.Case, async: true`, los módulos de prueba se ejecutan al mismo tiempo, cada uno en su propio proceso, lo que reduce el tiempo total. `CuentaTest` podría usarlo, porque solo prueba funciones puras. `BancoTest` no, porque todas sus pruebas comparten el proceso `Banco`, que está registrado con un nombre.

### Versión 5 (reto)

**Nuevo requerimiento:** los clientes quieren transferir dinero entre sus cuentas. Agregue a `Banco` la función `transferir(origen, destino, monto)`, que devuelve `:ok` si la transferencia se hizo, o `{:error, razon}` si no.

Escriba primero las pruebas en `test/banco_test.exs`, véalas fallar y después implemente la función. Las pruebas deben verificar que:

1. Una transferencia válida descuenta el monto del origen y lo suma al destino.
2. Si el saldo del origen no alcanza, devuelve `{:error, :saldo_insuficiente}` y **ninguna** de las dos cuentas cambia.
3. Si la cuenta destino no existe, devuelve `{:error, :cuenta_no_existe}` y el origen **no pierde** el dinero.

Al final, `mix test` debe pasar todas las pruebas, sin importar cuántas veces lo ejecute.

*Pistas:*

- El `setup` solo abre una cuenta. Para la cuenta destino, abra otra dentro de la prueba con otro número que no se repita.
- Reutilice `Cuenta.retirar/2` y `Cuenta.depositar/2`, y compruebe que las dos cuentas existen **antes** de modificar el estado. Si el retiro ya se guardó y luego falla el depósito, el dinero desaparece.

# Mix

Hasta ahora, cada programa ha sido un script `.exs` que se ejecuta con `elixir`. Este enfoque es adecuado para programas de uno o dos archivos, pero a medida que el código crece presenta algunas limitaciones:

- Para reutilizar el módulo `Util` fue necesario compilarlo manualmente con `elixirc` y ubicar el archivo `.beam` en la carpeta de cada script, además de recompilarlo cada vez que `util.exs` cambiaba.
- En el chat fue necesario indicar a `iex`, uno por uno, los archivos que debía cargar.
- Las pruebas se realizaron manualmente, ejecutando el programa y revisando la salida.

**Mix** es la herramienta oficial de construcción y gestión de proyectos de Elixir, y resuelve estas limitaciones. Es el equivalente a herramientas como `npm` en JavaScript o `Maven` en Java.

## ¿Qué hace Mix?

- **Estructura del proyecto.** Todos los proyectos Mix siguen la misma organización de carpetas, lo que facilita ubicar el código fuente y las pruebas.
- **Compilación.** `mix compile` compila todos los archivos de `lib/`, sin importar cuántos sean ni las dependencias entre ellos, y solo recompila los que cambiaron.
- **Pruebas.** `mix test` ejecuta todas las pruebas del proyecto e informa cuáles fallaron.
- **Gestión de dependencias.** Para usar una librería externa basta con declararla en `mix.exs` y ejecutar `mix deps.get`. Las librerías de Elixir se publican en [Hex](https://hex.pm).

Para más información, puede consultar la [documentación oficial de Mix](https://hexdocs.pm/mix/Mix.html).

## Estructura de un proyecto Mix

Un proyecto Mix típico tiene la siguiente estructura de directorios:

```
my_app/
├── _build/              # Archivos compilados (generado)
├── config/              # Archivos de configuración (opcional)
│   └── config.exs       # Archivo de configuración principal
├── lib/                 # Código fuente de la aplicación
│   └── my_app.ex        # Módulo principal
├── test/                # Pruebas unitarias
│   ├── test_helper.exs  # Configuración de pruebas
│   └── my_app_test.exs  # Pruebas del módulo principal
├── .gitignore           # Archivos ignorados por Git
├── mix.exs              # Archivo de configuración del proyecto
└── README.md            # Documentación del proyecto
``` 

### Comandos comunes de Mix

Con los siguientes comandos podemos gestionar y trabajar con proyectos Mix:

```bash
mix new my_app          # Crear un nuevo proyecto Mix
cd my_app
mix compile             # Compilar el proyecto
mix test                # Ejecutar pruebas
mix deps.get            # Obtener dependencias (descargarlas)
mix run                 # Ejecutar la aplicación
mix help                # Mostrar ayuda sobre comandos Mix
```

### Creación y compilación de un proyecto Mix

En su terminal, cree un nuevo proyecto Mix con `mix new my_app` y abra la carpeta `my_app` en Visual Studio Code. Compare lo que se creó con la estructura anterior.

## Archivo `mix.exs`

El archivo `mix.exs` es el archivo de configuración principal de un proyecto Mix. Allí se indican el nombre y la versión del proyecto, la versión de Elixir que necesita y las librerías externas que usa. Así se ve, de forma resumida, el que crea `mix new`:

```elixir
defmodule MyApp.MixProject do
  use Mix.Project # Indica que este módulo es un proyecto Mix

  # Configuración del proyecto
  def project do 
    [
      app: :my_app,
      version: "0.1.0",
      elixir: "~> 1.18",
      start_permanent: Mix.env() == :prod,
      deps: deps()
    ]
  end

  # Configuración de la aplicación
  def application do
    [
        extra_applications: [:logger]
    ]
  end

  # Definición de dependencias externas
  defp deps do
    []
  end
end
```

## Módulo principal y aplicaciones adicionales

En los scripts, la ejecución comenzaba con la llamada a `main()` ubicada al final del archivo. En un proyecto Mix no existe esa llamada, ya que `mix run` no ejecuta un archivo en particular. En su lugar, el proyecto define un módulo de inicio, que utiliza `Application`. Modifique el archivo `lib/my_app.ex` para que se vea así:

```elixir
defmodule MyApp do
  use Application # Indica que este módulo es una aplicación OTP
    
    # Application necesita una función start/2. Esta función es el punto de entrada de la aplicación.
    def start(_type, _args) do
        IO.puts("Hello, Mix!")
        {:ok, self()}
    end
end
```

`Application` es un behaviour de OTP, al igual que `GenServer`. El módulo debe definir la función `start/2`, que Elixir invoca al iniciar el proyecto.

Para que Elixir sepa cuál es ese módulo, modifique la función `application` en `mix.exs` y agregue la opción `mod`:

```elixir
def application do
  [
    mod: {MyApp, []}, # Módulo principal de la aplicación
    extra_applications: [:logger]
  ]
end
```

`:logger` es la biblioteca estándar de Elixir para registrar mensajes (*logging*), y `extra_applications` indica que el proyecto la usa.

## Ejecución de la aplicación

Sitúese en la carpeta del proyecto y compílelo con:

```bash
mix compile
```

Luego, ejecute la aplicación con:

```bash
mix run
``` 

Debería ver el mensaje `Hello, Mix!` en la consola.

## Árbol de supervisión en una aplicación OTP

En las guías anteriores, los `GenServer` y los supervisores se iniciaban desde `main`, dentro de un script. En un proyecto Mix, lo habitual es que la función `start/2` de la `Application` **inicie un supervisor raíz**, que a su vez inicia y vigila los procesos de la aplicación. De esta forma, todos los procesos quedan supervisados desde el arranque del proyecto.

Por ejemplo, para que nuestra aplicación inicie automáticamente un `GenServer` `Contador` bajo supervisión:

```elixir
defmodule MyApp do
  use Application

  @impl true
  def start(_type, _args) do
    children = [
      {Contador, 0}   # el GenServer Contador se inicia con valor inicial 0
    ]

    # El supervisor raíz vigila a todos los hijos
    opts = [strategy: :one_for_one, name: MyApp.Supervisor]
    Supervisor.start_link(children, opts)
  end
end
```

Cuando se ejecuta `mix run`, Elixir llama a `start/2`, que arranca el supervisor raíz y este, a su vez, inicia el `Contador`.

Una `Application` que inicia un árbol de supervisión es la forma habitual de organizar las aplicaciones en Elixir. En este modelo, un supervisor puede gestionar otros supervisores y procesos, formando una estructura jerárquica que permite organizar y supervisar los procesos de la aplicación.

## Creación de pruebas 

Las pruebas se ubican en la carpeta `test`, en archivos cuyo nombre termina en `_test.exs`. `mix new` crea uno por defecto, `test/my_app_test.exs`. Reemplace su contenido por el siguiente:

```elixir
defmodule MyAppTest do
  use ExUnit.Case # Importa las funcionalidades de ExUnit para pruebas

  test "la suma funciona correctamente" do
    assert 1 + 1 == 2
  end

  test "la resta funciona correctamente" do
    assert 2 - 1 == 1
  end

  test "la multiplicación no da un resultado incorrecto" do
    refute 2 * 3 == 7
  end

end
```

Toda prueba en Elixir se define dentro de un módulo que utiliza `ExUnit.Case`. La función `test` define una prueba individual, y dentro de ella se usan aserciones, que son las funciones que verifican si un resultado es el esperado.

Para ejecutar las pruebas, use el comando:

```bash
mix test
```

Debería salir un resumen de las pruebas ejecutadas, indicando cuántas pasaron y cuántas fallaron.

### Aserciones más comunes

ExUnit ofrece varias funciones para verificar condiciones dentro de una prueba:

- `assert expresion`: la prueba pasa si la expresión es verdadera.
- `refute expresion`: la prueba pasa si la expresión es falsa.
- `assert_raise TipoError, fn -> ... end`: verifica que el código lance una excepción del tipo indicado.
- `assert_in_delta valor1, valor2, delta`: verifica que dos números estén dentro de un margen (útil para flotantes).

```elixir
defmodule CalculadoraTest do
  use ExUnit.Case

  test "dividir por cero lanza una excepción" do
    assert_raise ArithmeticError, fn -> 1 / 0 end
  end

  test "el promedio es aproximadamente correcto" do
    assert_in_delta 10 / 3, 3.33, 0.01
  end
end
```

### Agrupar pruebas con `describe`

Cuando se tienen muchas pruebas relacionadas, se pueden agrupar con `describe`:

```elixir
defmodule CuentaTest do
  use ExUnit.Case

  describe "depositar/2" do
    test "aumenta el saldo" do
      assert Cuenta.depositar(100, 50) == 150
    end

    test "no acepta montos negativos" do
      assert Cuenta.depositar(100, -50) == {:error, :monto_invalido}
    end
  end
end
```

### Preparar datos con `setup`

El bloque `setup` se ejecuta **antes de cada prueba** y permite preparar datos comunes, que se reciben en un mapa de contexto:

```elixir
defmodule InventarioTest do
  use ExUnit.Case

  setup do
    inventario = %{"P001" => %{nombre: "Laptop", precio: 1200}}
    {:ok, inventario: inventario}   # se inyecta en el contexto de cada prueba
  end

  test "el producto existe", %{inventario: inventario} do
    assert Map.has_key?(inventario, "P001")
  end
end
```

> ⚠️ **Pruebas concurrentes:** con `use ExUnit.Case, async: true`, los módulos de prueba se ejecutan de forma concurrente, cada uno en su propio proceso, lo que reduce el tiempo total de ejecución. Esta opción solo es segura si las pruebas no comparten recursos que puedan modificarse al mismo tiempo, como un proceso registrado con nombre (por ejemplo, la `Caja`) o un archivo.

Asegúrese de que el proyecto compile y se ejecute con `mix run`. Además, escriba al menos dos pruebas por cada operación de la Pokédex (registrar, buscar, actualizar y liberar), una para el caso exitoso y otra para el caso de error.

Estructura sugerida del proyecto:

```
pokedex/
├── lib/
│   ├── pokedex.ex            # Módulo principal
│   ├── pokedex/
│   │   ├── pokemon.ex        # Gestión de Pokémon
│   │   ├── movimiento.ex     # Gestión de movimientos
│   │   └── archivo.ex        # Persistencia en CSV
└── test/
    ├── pokedex_test.exs
    └── pokedex/
        ├── pokemon_test.exs
        ├── movimiento_test.exs
        └── archivo_test.exs
```
### Ejercicio 2

Convierta el sistema de gestión de tareas del Ejercicio 3 de OTP en una aplicación con Mix. Cree un proyecto Mix, defina un árbol de supervisión para el servidor de tareas y asegúrese de que el servidor se inicie automáticamente cuando se inicie la aplicación.

```
tareas_app/
```
